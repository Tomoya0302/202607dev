## -4.【2026-08-11夜、進行中】DRL方策（候補再ランキング型）の導入 + soft/priority診断

ユーザー指示「public_score>65に向けた開発方針を相談したい」を受け、文献調査

塞いだ結果、その荷物自体が未積載になるケースが増え逆効果）。診断（soft-on-softは
物理的に危険）は正しかったが、「候補スコアで避ける」という介入方針が誤りだった。
このプロジェクトが繰り返し踏んできた「位置レベルで候補を塞ぐと、局所的な不安定性より
重い代償（未積載）を払う」というパターンの新しい実例。

**`GH_PRIO_SHIFT`（−0.15/−0.3、`GH_PRIO_LATE=1`は維持）**: prio_viol%はほぼ無風
（family1ではむしろ悪化傾向、有意ではない）、fill/cogもわずかに悪化傾向
（family2の−0.3でcog t=−2.45・fill t=−2.16と境界的）。`_reorder_quality`が
`GH_PRIO_LATE=1`でカテゴリカルに「優先品は必ず最後尾」と並べ替えるのが先に効くため、
後段の`_soft_shift_order`の連続シフトでは実質動かせていない可能性が高い
（呼び出し順序: `_soft_shift_order(_reorder_quality(order))`）。v31の危険な前例
（cog −3.57→Public −7.30）を踏まえ、これ以上この方向を強める理由はないと判断。

**次にこの方向を追うなら**: 優先品の未積載問題（73%）自体は実在するが、
「順序を動かす」アプローチはPRIO_LATE/PRIO_SHIFTの両方で行き詰まった。次の一手が
あるとすれば「優先品を無理に早められないなら、優先品向けの候補生成・階段制約側で
専用の緩和を検討する」といった位置レベルの再設計になるが、これは§27.1で確立した
「cog/stabilityにローカル接地が無い」という構造的制約に真正面から踏み込むため、
慎重な検討が必要（この方向は一旦保留を推奨）。

## -3.【2026-08-11、結論】Sequence Triple投資は終了——v52を維持、次は別方向へ

§-2/§-1（下記）でSequence Triple（3順列によるcombinatorial同時配置decode）を
実装・検証したが、**最終的にv52を上回れず、この方向の追求は終了した**。
**以下の§-2/§-1にある「次にこの方向を進める場合は必ず読むこと」は過去の
指示であり、もう有効ではない。次セッションはこの方向をデフォルトで継続
しないこと**（新しいアイデア・レバーがあるなら別だが、ユーザーに確認してから）。

**最終結論の根拠**（詳細は`docs/design_sequence_triple_2026-08-10.md`§11-13）:
- n=20タスク（逐次実行、CPU競合バイアスを排除して確定）で**19/20（95%）は
  v52既定（floor）が個数・体積とも優位**。唯一の例外（f1_0000）も個数差1・
  体積差+0.17というごく僅かなマージン。
- §4.4の非退行floor比較機構は正しく機能しており、劣る候補を適切に不採用に
  し続けた（実装バグを2件発見・修正済み、§11.5.1）。
- soft veto（hard品をsoft品の上に置かない制約）は実装・実測確認済み（§11.8/13.1、
  hard-on-soft違反0件）。優先品の位置誘導は未実装で系統的な効果なし（§13.1）。
- ブリッジ配置は「一度も発生しない」ではなく「稀にしか発生しない」が正確な
  理解（§13.2で訂正）。80品規模の実タスクで1件自然発生を確認したが、
  seed/SA構造の弱さという主要ボトルネックを覆すには至らない。
- **検証手法自体の教訓**: wall-clock予算に依存する比較（floor vs candidate）を
  8並列バッチで実行すると、コスト非対称な処理（floorの実物理検証）だけが
  不当に不利になるバイアスが生じる（§12.4）。同種の比較は必ず逐次実行するか
  CPU分離を保証すること——今後、時間予算ベースの新機構を検証する際の
  一般的な注意点として記録しておく。

**コードの扱い**: `seq_triple.py`本体・テスト3件・design doc・可視化スクリプト
（`visualize_run.py`）はコミット済み（`f56e10f`、2026-08-11、記録目的）。
`GH_SEQ_TRIPLE`は既定OFFのまま、`agent.py`側のフック自体はこのコミットに
含まれていない未コミット差分として作業ツリーに残っている（v50ベースライン
改定など無関係な既存差分と混在しているため、意図的に分離）。提出物・
本番既定挙動への影響は一切ない。

4. 重複id混入・headroom_probe拒否による荷物の消失（多層シード実装時、

   固定`verify_reserve_s=25秒`を独立に確保）へ合わせて修正し、
   real_000・f2_0000の両方でv52既定と完全一致する結果へ回帰することを
   確認した。**この安全機構自体の欠陥は、`GH_SEQ_TRIPLE`が既定OFFかつ
   一度も提出していなかったため実害は無かったが、もし見過ごされたまま
   有効化されていたら実際に本番退行を引き起こしていた可能性がある。**

### 現状の限界（性能面）
初期解（棚パッキングシード、多層・マルチスタート込み）は、cut/棚構造を持つ
実タスク規模（real_000のfamily1相当、41品/1コンテナ）でfloorに届かない

しまっており、後者を単独で評価できていない。

### n=99×3族ベンチは未実施
現状のシード品質では大半のタスクでfloorに負けて`None`が返る可能性が高く、
検証の情報量が薄いため意図的に見送った。design文書§11.6に次セッションへの

### 【重要、ユーザー指摘を受けて追加検証】ブリッジ配置は実際には一度も
発生していないと判明（design文書§11.7）
§32.3が当初期待していた「短い先読みの逐次貪欲では見逃すブリッジ配置
（高さの異なる支持面にまたがる配置）を、combinatorialな同時最適化で
発見する」という**Sequence Tripleの核心的な価値提案は、本セッションでは
検証できていない**。診断コードで確定配置を走査したところ、シード単体・
SAの近傍操作300回ランダムウォークのいずれでもブリッジ発生**0件**だった。
原因は構造的: (1) 列構造シード（`_shelf_columns`）は各列が1つのfounderの
上にしか積まない設計で、支持整合を保証する代償として初期解からブリッジの
可能性を排除していた。(2) SAの近傍操作（swap/insert/segment-reverse）は
汎用の順列操作でブリッジを狙って設計されていない。「試したが効果が薄かった」
のではなく「メカニズム（`land=max(...)`、既存heightmap.pyと同じロジック）は
存在するが、シード/探索がそれを一度も提案していない」が正確な現状。
次にこの方向を追うなら、ブリッジを明示的に狙う近傍操作・シード後処理の
追加が必須（design文書§11.7参照）。

提出物・既定値への影響は一切なし（`GH_SEQ_TRIPLE`は既定OFF、コミットも
していない——CLAUDE.mdの方針どおりユーザー明示指示待ち）。

## 7. 絶対に守るルール（過去の失敗から）

1. **提出前に §11 の7条件を確認**（性能実測・cog・n≥99・族別頑健・placement非依拠・
   soft非悪化・観測域内）。**族は3つある**（`optimize=True/look_ahead=1` の1容器・2容器、

2. **予測を事前登録してから提出**（上下両方向をカバー、§11.3）。
3. **局所 cog は本番 cog を予測しない。** ctr_mean・公式定義cog・局所cog の

   一方 **np は転移する**（局所np↔本番np r=0.938）ので判定は np/fill 主体で行う。
4. **n=30 の t≈2 は信用しない**（`ts25`・v40 で偽陽性、§6.5/§15.3）。
5. **No-Go 判定は前提条件つき。** §19.9/§19.10 で 2 件が覆った

   前提レバーが動いたら No-Go 一覧は再評価すること。
6. **「位置レベルは高リスク」は過度な一般化だった**（2026-08-01 版の本文書の規則1）。
   実際に大退行した3件はいずれも**着地面スコアの重み微調整**で、局所効果は ±1 fill 程度。
   §19 の階段制約は同じ `heightmap.py` の変更だが**構成法（硬い制約）**であり、
   3族すべてで fill が有意に改善した。**機構レベルではなく効果量と検証の質で判断すること。**

## 8. 次に試す価値がある方向

### 8.1 【結果判明・失敗】v47 は過去最悪級の大退行（findings §21）

v47（`STAIR_K=1.15` + `STAIR_SLACK=0`、他は v46 のまま）を提出した結果、
**Public 54.48（v43 比 −7.02、v46 比 −6.11）。cog −15.39 を筆頭に全サブスコアが
v46 より悪化した。** 局所 n=30×2族は v47 を「両族とも cog がほぼ中立」と判定していたが
（旧§20.7）、本番はこれを完全に裏切った。**SKU寸法仮説（`STAIR_K` で cog が回復すると
いう予測）は反証された。** 機構の仮説（大きい荷物ほど `STAIR_K` の slack を多く得て、
質量加重の cog に最も効くクラスで層規律が緩む）は findings §21.3 参照、未確証。

**v48・v49 の追加提出は保留する。** 局所n=30の順位づけ（v47が最良）が本番で裏切られた
以上、同じ軽い検証水準で残り2候補を提出する根拠がない（詳細は §21.6）。
`submit_20260805_v49_stair_only.zip` はビルド済みだが、**提出しない方針**
（ユーザーが別途判断するまで保留）。

**手続き上の教訓**: v46 は n=99×3族・594実行を経て提出されたが、v47/v48/v49 は
n=30×2族のみ（課題Bを含む family3 を欠く）で提出判断した。**次に何か提出するなら、
「診断提出だから軽くてよい」を適用せず、§11条件3（n≥99）を最初から満たすこと。**
既存レバーの計算方式そのものを変える変更（絶対値→比例など）は、順序の微調整より
リスクが高いという教訓も残った（findings §21.4）。

### 8.2 局所 np はまだ 0.70 前後（上限 1.0）

階段制約は貪欲スコアへの*フィルタ*にすぎず、`optimize()` が持つ 180秒・全情報を使った
**構成的レイアウト計画**（層を奥から手前へ完成させる割付を先に決め、`policy()` はそれを追う）
は未着手。伸びしろが最も大きい。§8.3 のトーテムポール案はこの方向の具体案。

### 8.3 【第1試作・失敗】トーテムポール構成法は純粋な属性ベース順序レバーでは近似できない

ユーザー発案・2026-08-05 検討。`docs/idea_totem_stacking_2026-08-05.txt` に詳細。
奥から一柱ずつ完成させる構成（ブリッジなし）にすれば、§19 の到達可能性不変条件
（各xレーンで天面が扉へ向かって単調非増加）を**スコアペナルティのキャリブレーションに
頼らず構造的に自動満足**できる——`HARD_MAX_RUN`（構造的制約）が唯一クリーンに効き
`HM_W_SOFT_VIOL`（相対ペナルティ）が一度も拘束的でなかった、という既存の経験則
（§19.9、構造的制約 > スコアペナルティ）に沿う。この着想自体は棄却されていない。

**第1試作（`GH_FOOTPRINT_GROUP`、HF-036）は n=30 で即座に大失敗した**
（両族 Δnp −19〜−20pt、Δsoft −63〜−65、t値は二桁。findings §22）。**提出はしていない**
——段階案どおり軽い局所チェックで止められた点は機能した。

**失敗から分かった、より根本的な壁**: 実装は荷物の設置面積（属性）でグルーピングしたが、
ユーザー原案の核心は「**奥から**」という**空間的な深さ**の話だった。`look_ahead=1` の下で
純粋な属性ベースの順序レバー（`TALL_SHIFT`等と同じ形）は、荷物がどの深さへ着地するかを
知りようがなく、**「奥から」を表現する手段が原理的に無い**。この方向を続けるには:

1. **heightmap.py の候補生成に手を入れる**（位置レベル）——§16.4/§21で5連敗中のカテゴリ
2. **`optimize()` 時点のシミュレーションベース順序探索**（§13 `GH_ORDER_SEARCH`の系譜）
   ——空間状態は見えるが、n=30の境界シグナルが本番非再現だった前例（v40）がある

**どちらも無条件に安全ではない。次にこの方向を進めるかどうか、進めるならどちらの経路を
取るかはユーザー判断待ち**（findings §22.5）。進める場合、v47 の失敗を踏まえ
§21.4の教訓（診断提出でも軽い検証で済ませない、n≥99×3族が必要）を最初から適用すること。

### 8.4 階段制約下での重み再調整（優先度低下）

`HM_W_DEPTH=4.5` / `HM_W_HEIGHT=6.0` / `TALL_SHIFT=2.0` はすべて「封鎖される体制」で
調整された値。`TALL_SHIFT`（薄物先行）は「厚物が最後に来て死ぬ」ことの緩和策でもあったので、
死ななくなれば最適点が動く。**ただし v47 の失敗で「階段制約下でcogが安定した構成」自体が
まだ得られていない**ため、この再調整に着手する前提が整っていない。§21.3 の機構仮説の
検証（診断のみ、提出なし）を先に行う。

### 8.6 【更新、2026-08-08】soft転倒の因果は確認したが、4種のレバー試作すべてNo-Go（findings §25）

soft転倒の機構自体は因果的に確定している（§25.4、`--hard-soft`アブレーション）が、
それを安全に活用する方法を4種試して**全滅**した:

1. `GH_HM_W_TILT_SOFT`（新規、位置減点型）— §16.4「位置レベルは予測不能」の4例目失敗。
2. `GH_SOFT_THIN_SHIFT`（既存流用、順序型）— 機構が発火せず無風（傾き不変）＋family2で副作用。
3. `GH_HM_MAX_ROUGH`（既存流用、位置硬制約型）— **本検証で唯一「本物」の機構**
   （傾き−16〜−23%、cog+3.19〜+3.56、n=30×2族）だったが、npコストが構造的に不可分
   （しきい値を緩めても比例して両方縮む）。フォールバック付き再設計（`stair_bad`と同型の
   「消さず・大減点・desperate段のみ解禁」）でnpは守れたが、cog利得も同時に消えた
   （番人定数1e6が事実上の恒久除外として機能してしまうため）。
4. `GH_HM_W_FLAT`↑（既存の**本番実績あるレバー**、連続重み型）— 逆方向(0.6)がv39で
   Public−3.40・cog−5.73と実証済みなので、引き上げ方向(2.0/2.4)は理論的に最有力候補
   だった。n=30ではcogが弱い正の信号（t=1.3〜1.9）だったが、**n=99×3族へ昇格すると
   6条件すべて非有意、family3では符号が逆転**——§6.5「n=30のt≈2は信用しない」の
   5件目の再現。

**この方向は一旦終了。** 次に試すなら:

1. `--hard-soft`アブレーションが示した「fill/cogは動くがnpは動かない」という分離は
   まだ活用されていない情報として残しておく。
2. cogへの寄与の大きさを本番規模で切り分ける（§25.4の1〜1.5ptは全soft品の接触を
   完全無効化した上限値。実際のレバー変更でどれだけこの経路が動くかは未測定）。
3. 診断ツール自体（`tilt_diag.py`/`tilt_batch.py`/`tilt_report.py`）は今後の soft
   関連レバー審査に再利用できる（例: 新レバー候補が傾きを悪化させていないかの副検定）。
4. **むしろ§8.2（構成的レイアウト計画、局所np上限0.70対1.0の伸びしろ）など、
   soft/roughness以外の軸へ戻ることを推奨する。**

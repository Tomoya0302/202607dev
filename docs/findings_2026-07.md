## 2. 採点構造

### 2.1 公開されている部分

* 集約は「**加重平均**」（`simulator/README.md:375`）。**重みはリポジトリのどこにも無い**（本紙 §4.4(2) がプラットフォーム側提示と明記）
* `fill_score` は完全に仕様化（`evaluator.py:70` + `containers.py:101-114`）。**本番と同一コードがローカルにある**
* `cog_score` の定義（`analysis/platform_score.py::compute_cog` が公開定義の実装）:
  ```
  z_com = Σ(mass_i · pos_z_i) / Σ mass_i
  cog   = 100 · (1 − (z_com − z_floor)/(z_top − z_floor))     # z_floor/z_top は容器**外**寸
  ```
  **質量加重**・**全体で1つの重心**・**置いた荷物だけを数える**
* `placement` / `soft` の違反定義（**未積載も違反に数える**）
* `num_placed_items` が他4項をゲートする（README:382）が**閾値は非公開**

### 2.2 推定した実効重み

22 提出のサブスコアと Public から、非負・和1 制約付き最小二乗（v31 を外れ値として除外した15点）:

| | fill | cog | stability | placement | soft |
|---|---|---|---|---|---|
| **実効重み** | **0.268** | **0.261** | 0.168 | **0.145** | 0.158 |

LOO 残差 RMS **0.425** / 最大 1.07（等重み 0.566 より良い）。**等重み 0.2×5 は誤り。**
発見の入口は「残差が placement と r = −0.722 で負相関」（v31 を除いても消えない）。

### 2.2.1 21点で再推定すると placement は 0.000（訂正）

v38 を含む 21 提出で解き直すと **fill 0.369 / cog 0.264 / stab 0.177 / placement 0.000 / soft 0.191**。
**placement は Public に寄与していない**（「符号が不定」ではなく重みゼロ）。これが v31 で
placement を +11.65 上げて Public −7.30 になったことの説明。

**⇒ 推定重みによる合成目的は判定に使わない。本番で実測できた事実だけを使う（§11 参照）。**

## 4. 検証済みの機構

### 4.1 効いたレバー（本番実測）

| 提出 | 変更 | ΔPublic | 機構 |
|---|---|---|---|
| v14→v24 | `PRIO_LATE=1` | **+1.76** | 優先品を末尾へ→積み残す→cog +7.40 |
| v24→v25 | `HEAVY_SHIFT=0.3` | +0.43 | 質量ランクで連続遅延 |
| v25→v29 | **`TALL_SHIFT=2.0`** | **+3.87** | **薄い荷物を先に流す**（最大の単発利得） |
| v29→v32 | `PRIO_RESERVE=1.0` | +0.20 | 優先容器の上部を予約 |
| v32→v35 | `SOFT_SHIFT=-1.3` | +0.50 | soft を前倒し（未積載 34.7%→3.8%） |
| v35→v38 | **`PRIO_RESERVE=0`**（予約撤去） | **+1.00** | fill +0.63 / np +0.87pt を得て cog −1.57 を払う |

**6 件すべてが順序系。位置スコアの変更で効いたものは 1 件も無い。**

v38 は診断目的（混合比の測定）で出したもので、**改善を予測していなかった**。
局所 2容器族の合成目的は ΔS −0.708（t=−5.24）で**却下**と判定していた。
基準を v38 に取り直すと、**過去 31 設定すべてが fill/np で v38 に劣る**
（v35 −1.39/−2.21pt、v37 −1.58/−2.58pt、d02 −3.91/−5.81pt）。
**cog 重視の合成目的が、53 設定にわたってこの方向を却下し続けていた。**

### 4.1.1 全レバーが山頂にあることの確認（ablation）

現行 v38 の 5 レバーを 1 つずつ動かし、両族 138 タスクで測定した（2容器族の Δfill）。

| レバー | 山頂 | 両側の測定 |
|---|---|---|
| `TALL_SHIFT` | **2.0** | 0 −4.18(t=−9.5) / 1.6 −0.73(t=−2.6) / 1.8 −0.67(t=−2.4) / 2.2 +0.20(ns) / 2.5 −1.86(t=−5.8) |
| `HEAVY_SHIFT` | **0.3** | 0 −0.70(t=−2.3) / 0.15 −0.12 / 0.6 −1.50(t=−5.2) |
| `SOFT_SHIFT` | **−1.3** | 0 で fill −1.44 / np −4.63pt / soft −24.06 |
| `PRIO_RESERVE` | **0** | 1.0 / 1.5 / 1.8 / 2.2 すべて劣る |
| `PRIO_LATE` | **1** | 0 で fill −1.21(t=−4.4) / np −1.31pt |

**`TALL_SHIFT` を切ると np が −15.00pt（t=−24.7）落ちる。** v29 で +3.87 を生んだ機構が今も最大の柱。

**dr10（9タスク）で「ノイズ」に見えた `HEAVY_SHIFT` が、99タスクでは有意に効いていた**
（Δfill −0.70、t=−2.3）。標本数不足による誤判定を、この ablation が止めた。

`TALL_SHIFT=0` は Δctr +0.0062（t=+2.8）で **cog ガードが正しく発火**した初の例。

### 4.2 `look_ahead=1` が意味すること

`items.py` を読むと `max_space` は単なる補充トリガで、プールは常に 1 個。**荷物選択の自由度はゼロで、大域制御は `optimize()` が返す順序だけ。**

これで位置系 No-Go 9 件（候補拡張・層規律・z非依存シャドウ・z帯シャドウ・GRASP・ビーム・リーチャビリティ先読み・格子解像度・スラブ跨ぎコスト）の共通原因が説明される。先読みが選択を 0.7% しか変えなかったのはプールに 1 個しか無いから。

### 4.3 v29 の導出は proxy に基づいていた（重要）

v29 の +3.87 は「cog は重みなし平均 ⇒ Σbottom の最小化」という導出から得た。しかし**公式定義は質量加重**（§2.1）で、4 点すべて違う。`ctr_mean`（重みなし・内寸正規化・比の平均）が偶然相関していただけ。

そして **v37 で `HEAVY_CEIL=0.70`（公式定義どおり質量重心を下げる）を提出すると、局所公式cog +0.42 に対し本番 cog −0.83 で符号反転、Public は 60.00 のまま。** ⇒ **cog の支配は相関であって因果ではない。**

## 4.5 計算資源の配分 ―― レバー空間の外にある軸

### 4.5.1 エージェントは時間予算を半分も使っていない

| | 実測 | 要件 | 使用率 |
|---|---|---|---|
| `policy`（1ステップ最大） | 4.30〜4.51 秒 | 10 秒 | **45%** |
| `optimization` | 35〜62 秒 | 180 秒 | **34%** |

**未使用の予算を候補幅に振り向けられる。** `GH_HM_BREADTH_MUL` を実装（既定 1.0）。
`HM_CASCADE` 第3段の desperate 幅（per_bin 14 / coarse 250）を上限に倍率で刻む。

| 倍率 | pmax 増加率 | 本番換算 | Δfill | Δnp | Δsoft |
|---|---|---|---|---|---|
| 1.3 | — | — | +0.26(1.3) | +0.66pt(2.3) | −1.60(**−2.6**) |
| **1.5** | **1.45 倍** | **6.5 秒 ✓** | +0.32(1.6) | **+0.81pt(2.9)** | −1.54(**−2.2**) |
| 1.8 | **4.24 倍** | **19.1 秒 ✗** | +0.52(2.4) | +0.92pt(3.0) | −2.91(**−3.3**) |
| 3.5（全開） | 3.2 倍 | 14.4 秒 ✗ | +0.47 | +0.58pt | — |

**pmax は最大値なので幅に対して非線形に跳ねる。** 1.5 で 1.45倍、2.0 で 2.07倍だったので
1.8 を「1.8倍前後」と予想したが**実測 4.24倍**。**性能要件は必ず実測する。**

⇒ **使える上限は倍率 1.5。** そこでは np が有意に改善するが（+0.81pt, t=2.9）
**soft が t=−2.2 で基準をわずかに超える**ため提出保留。

### 4.5.2 幅と soft はトレードする（機構）

候補が増えると「スコアは高いが soft の上に載る」配置が選ばれやすくなる。
`HM_W_SOFT_VIOL=40` の減点は**相対的**なので、候補が増えれば減点を上回る候補が現れる。
**幅を狭めても soft は改善しない**（1.3 で −1.60、1.5 で −1.54）ので、
soft 低下は幅の大きさに比例せず**幅を広げた時点で生じる構造的副作用**。

### 4.5.3 失敗時のみの幅拡大は No-Go

カスケードは最初の可行候補で止まるので「幅が要るのは諦める瞬間だけ」と考え、
`GH_HM_WIDE_ON_FAIL` を実装した。結果は **pmax 3.2倍で fill/np が完全に不変**。

諦める瞬間には残り空間が真に搬入不能（棄却候補1,877件を本物の validator に通して0件合格）。
**`wide1` の利得は「諦めを救う」効果ではなく「早い段階で選ぶ候補が変わる」効果**であり、
遅延版では取れない。⇒ 常時広げる必要があり、そこで時間予算が制約になる。

### 4.5.4 実験基盤の並列化（7倍）

**16コア機を 2 並列で使っていた。** さらにコンテナのメモリを 2.7 GB と見積もっていたが
**実測 72 MB**（37倍過大）。両方修正して **14 並列 = 当初の 7 倍**。

| | 1設定あたり |
|---|---|
| 2 並列（当初） | 約 15 分 |
| 14 並列（現在） | **約 3〜5 分** |

**律速は CPU（16コア）。メモリは 22 GB / 72 MB = 300 本以上入る。**
`scripts/eval_chunked.py` がタスクを 14 分割して1設定を並列評価する（99タスクを約13分、逐次100分）。
**これがなければ 99 タスクでの検証自体が不可能だった。**

## 6. 測定方法論（最も価値のある成果）

### 6.1 局所予測子はすべて単独では破れた

|---|---|
| 局所 fill | Public と r = −0.141 |

| 局所 soft | v36（局所 +10.50 → 本番 **−15.75**） |
| 局所 ctr_mean | v34・v35（符号反転） |

| ctr_mass / 沈降変位 / 傾き / 計画スループット | v34 で 8 指標すべて良好なのに −4.50 |

### 6.2 有意性検定が 7/7 の遷移を説明した

タスクごとの差の t 値（`Δctr_mean`、課題A 9タスク、対応のある差）:

| 遷移 | t 値 | 本番 ΔPublic |
|---|---|---|
| v25→v29 | **−11.10** | **+3.87** |
| v29→v32 | **−3.58** | **+0.20** |
| v32→v35 | +1.62 | +0.50 |
| v29→v31 | **+3.47** | **−7.30** |
| v35→v36 | **+2.27** | **−6.00** |
| v33→v34 | −0.27（信号なし） | **−4.50** |
| v35→v37 | −1.39（信号なし） | ±0.00 |

**「t ≤ −2 のときだけ提出」を遡って適用すると、利得 +4.07 を保ち損失 −17.80 を全て防ぎ、代償は v35 の +0.50 だけ。**

out-of-sample 検証（未使用の seed 31337、30タスク）でも再現: v36 t=+3.72（却下）、v37 t=−0.49（信号なし）。in-sample より鋭い。

### 6.3 しかし `ctr_mean` 単独は gameable

**ctr は置いた荷物の平均なので、置く数を減らせば下がる。** `PRIO_RESERVE` を 0.5→1.0→1.5→2.2 と上げると t が +3.25 → 0 → −4.39 → **−10.06** と単調に鋭くなる一方、np が **−5.00pt** 落ちる。30 設定中 12 設定がこの型で「採用可」と出た。

### 6.4 正しい目的関数

実効重みで 5 項を 1 スカラーに合成する。**置く数を減らすと fill が落ちるので gaming できない。**

```
S_t = 0.268·fill_t + 0.429·cog_t + 0.145·placement_t + 0.158·soft_t
```
（stability は cog とほぼ同一なので cog 側に 0.168 を合算）

fill は本番と同一コード、cog は公開定義の厳密計算、placement / soft は公開定義を contacts から再構成。**すべて dump から計算でき、物理の再実行は不要。**

### 6.5 標本数が足りていなかった

| タスク数 | `ctr_mean` の標準誤差 | 検出限界（2×SE） |
|---|---|---|
| 9〜10 | 0.003〜0.008 | 0.010 |
| 30 | 0.0036 | 0.004 |
| 99 | 0.0020 | 0.003 |

**`ts25` は 30 タスクで t=2.15 → 99 タスクで t=0.41 に崩れた**（効果量も +0.285 → +0.141 に半減）。偽陽性 1 件を止めた。

placement と soft は少数個数の百分率（優先品 5〜7 個、soft 約 24 個）なのでタスク間分散が巨大。**5 項の完全な合成を有意に判定するには n=55〜450 が必要。**

### 6.6 混合比は識別できない

Public が課題B/C を含むなら順序系レバーはその部分で完全に不活性（`app.py:58` の `if env.optimize:`）。よって
`ΔPublic = α_A · ΔS_local` の傾きが混合比を与えるはずだが、**8 遷移で回帰すると α_A = 0.19 ± 0.61 で識別できない。**

原因は比が 0.00〜0.69 と −4.8〜−13.0 に分裂すること。**希釈では符号は変わらない**ので、少なくとも 2 成分（希釈 + 局所で見えない損失）が必要。

部分的な読み: 両族で効く `TALL_SHIFT` の比 0.69、2容器族だけで効く `PRIO_RESERVE` の比 0.28 ⇒ **2容器族のシェアは約 0.4、1容器族が約 0.6**（2 点なので標準誤差なし）。

### 6.7 混合比が非公開なので族別の頑健性で判定する

プール評価は暗黙に 50/50 を仮定する。正しい基準は:

> **片族で有意に改善（t ≥ 2）かつ他族で悪化しない（t > −2）**

これなら混合比が何であれ成立する。

## 8. No-Go 一覧（機構つき）

### 8.1 位置スコア系（`look_ahead=1` により原理的に無力）

候補拡張 / 層規律 / z非依存シャドウ / z帯シャドウ / GRASP / ビーム / リーチャビリティ先読み / 格子解像度 / スラブ跨ぎコスト — 計 9 件。共通原因は §4.2。

### 8.2 構造的に還元される

**奥→手前の一方向フロンティア制約**: レーン単位のフロンティアは高さを問わないので、深さ j に置いた直後そのレーンの frontier = j となり**同じ深さへの積み上げが禁止される** → overload の fill が 32.57 → 10.67。正しい「高さ帯ごとのフロンティア」は **`check_l_path` そのもの**。

**層積みプランナ**: 各層の高さをその層の**最厚**荷物に量子化するので薄い荷物の上に無駄が残る。DBLF は各荷物を個別の最低点に置き、それが Σbottom の貪欲最適。実測で層積み ctr 0.4074 対 貪欲 0.3851。
動機にした「理論下限 0.2115」は **artifact**（v25 が置いた約26個だけを3層に積んだ値で、貪欲の約55個とは配置数が違う比較だった）。

### 8.3 幾何的に不可避なトレード

**局所 fill と局所 ctr_mean は r = +0.93**（47設定でも +0.826）。体積を詰めるには高く積むしかない。
**「密に詰めて同時に低くする」構成は存在しない。** cog を下げる手は必ず fill/np を払う。

**fill の床除外は不可避**: 8隅すべてが全境界面から 5mm 以上内側でなければ計上されない（面0 の法線 [0,0,−1] が z=thickness）。接地物は必ず除外。実測で配置の 25.3%・体積の 22.5%。回収可能なのは側壁 11 個 + cut 2 個 = **+0.97 fill** のみ（当初 cut 斜面に 49 個の余地があると見たが、46 個は既に床で除外されていた）。

### 8.4 性能要件違反

**候補幅拡大**（`HM_STRAT_PER_BIN_DESP=14` / `HM_COARSE_TOPK_DESP=250` が読まれていないのを修正）: 局所 pmax 0.253 → **0.806 秒（3.2倍）**。本番 4.51 秒に掛けて **約 14 秒で 10 秒要件を超過**。指標も改善しない（fill +0.59 / np −2.1pt）。

### 8.6 学習手法について

| 手法 | 必要評価数 | 判定 |
|---|---|---|
| 手調整レバー | ~50（実施済） | 5回中2回大敗 |
| ベイズ最適化（本番オラクル） | 50〜100 | **11点/9次元で予測力ゼロ**（LOO 3.65 対 自明 3.68） |

## 13. 方策3: 忠実 window リプレイによる順序探索（HF-030、実装済・既定OFF）

`optimize_order`/`_greedy_replay`（dead code、旧 EMS パイプライン）を使わず、`order.py` に
`search_order_composite` を新規実装した（`agents/heuristic/packing_core/order.py`）。
`agent.py` に `GH_ORDER_SEARCH`（既定 `0`）で配線。**既定 OFF では v38 と `fill_score`/
`num_placed_items` が全5ローカル課題でビット同一**（変更前後を `git stash` で分離して確認済み）。

### 13.1 前提の訂正（実装前の実測で判明）

当初案は「`plan_order_forward_sim`（全可視 heightmap 貪欲）を評価器に GRASP+山登りで
数百回探索」だったが、これは **findings §8.5 の `GH_ORDER_OBJ=score` と同一実験**（この
env var は `plan_order_forward_sim` にしか存在しない）で、既に ΔS≈0 と判定済みだった。
実測（c01, 41品目/1容器）でも1リプレイ **7.4〜8.1秒**、`GH_ORDER_GRASP=50`/60秒予算で
**7回**しか回らない（findings の「22秒×6回」と同じ天井）。

原因は評価器の性質: `_build_models_ranked` が pool を体積降順に再ソートするため、
`plan_order_forward_sim` は「候補順序を評価する」機構ではなく「heightmap 自身に順序を
生成させる」機構であり、入力順序への感度が弱い（SKU内タイブレークのみ）。

**修正**: 実 `policy()` と同じ `look_ahead=1` で `order` を逐次消費する忠実リプレイ
（`_replay_arrival_window`、現行 `decide_placement` を使用、EMSなし）を新規実装。
`ContainerHeightModel` は毎回 `placed` から高さを再導出し `space.height` を読まないため、
`containers` は複数リプレイ間で読み取り専用に共有できる。実測（c01, window=1）:
**1リプレイ約1.06秒**（全可視版の**約1/8**）。80品目/2容器級でも実測約2.2秒
（c03, 41品目/2容器）。170秒予算で **数十〜100+回の評価**が可能——findings §8.5 が
突き当たった天井（6回）を構造的に回避する。

干渉**（既配置との接触・validator 判定）を予測できない。これは「サロゲート忠実度」

とは別の限界。§11 が要求する運用規則（性能実測・n≥99・族別頑健・観測域内）は本機構にも
**そのまま適用が必須**であり、c01/c03 の1課題ずつの結果だけでは方向すら判定できない
（§6.5「9〜10タスクの検出限界」と同型）。

### 14.1 既存知見の裏付け（公式ソースでの確認）

* **課題の荷物構成は配布サンプルと厳密には一致しない**（Q8-3）: 「荷物数の範囲およびタイプ

* **一度置いた荷物は移動・回収不可**（Q4, Q9）。エージェント設計（一方向の逐次配置、

### 14.2 新規の知見（本ドキュメント未記載）

* **荷物の重心は幾何中心（直方体の対角線交点）で確定**（Q6）。「手荷物は直方体を前提とし、
  全ての重心は対角線の交点となる」。本セッションで実装した `bench_run.py::_compute_cog`

* **摩擦係数は安定性評価（揺らしテスト）に関与する**（Q3）。「摩擦係数は配置時の荷崩れ
  リスクや評価時の揺らしテストの安定性にかかわる要因」「手荷物の上に手荷物を配置する場合
  などにおいて、より安定な配置になるよう積み付け指示を」。**stability サブスコアに対して
  摩擦係数（SKUごとに固定値、§gen_tasks.pyの`_SKU_TABLE`参照）を明示的な特徴量として使う
  レバーは、探索してきた限りこれまで存在しない**（§4 の効いたレバー一覧はいずれも
  順序・優先度ベースで摩擦係数を参照しない）。未探索の軸として記録する。
* **コンテナ外への意図的な配置によるエピソード早期終了は「実装上可能だが推奨されない」**
  （Q8-2）。運営は明示的に「有利になるとは考えていない」と回答。悪用余地として検討する
  必要はない（既存の emergency action・watchdog 設計は早期終了を狙う設計になっていない
  ため、現状追加対応は不要）。
* **課題ごとに別プログラムを提出することは不可。1つの汎用プログラムが全課題に対応する
  必要がある**（Q14）。ただし「最初に渡されるコンテナや手荷物の情報から（内部で）切り替える
  ことは可能」。現行の `Agent`（`optimize`/`lookahead_k`/`container_list` を見て分岐する
  設計、§3.1「課題A = optimize=True + look_ahead=1」による内部分岐）はこの制約に適合済み。
* **非Python実装（C/C++/Rust等をPythonから呼ぶ形）も許可**（Q13、配布Dockerイメージに
  合わせてビルドする前提）。速度が課題になった場合の逃げ道として記録（現状は性能要件を
  満たしているため未検討、§11条件1）。

## 15. 摩擦係数×安定性の探索（HF-031、既定OFF・実装済み）

§14.2 で見つけた未探索軸（運営QA Q3: 摩擦係数が揺らしテストの安定性に関与する）を追う。
**stability_score はこのリポジトリに実装が無く（サーバー側のみ）、ローカルで真値は計算
できない。** そこで独自のローカル揺らし test proxy を新規実装し、方向性だけを見る。

### 15.1 実装

* **`scripts/bench_run.py::_run_shake_test`**: settle 済みの全荷物へ交互方向（+X/−X）の
  横方向速度キックを3サイクル与え、静定後の変位を計測する（`--shake-test` フラグ）。
  **公式 stability_score の再現ではない**（振幅・周期・軸は非公開、README §3.4 は概説のみ）。
  `mean_disp`/`max_disp`/`n_disp_gt_2cm`/`n_disp_gt_5cm` を返す。
* **`GH_HM_W_HARDHARD`**（`heightmap.py`、既定 0=無効）: 非soft品を非soft品の露出上面へ
  着地させる窓を減点する新規レバー。7SKU閉集合は is_soft=False の全SKUが
  lateralFriction=0.4 固定（is_soft=True は0.6-0.8、床は0.8固定）なので、
  hard-on-hard 接触が系内最低摩擦の組合せになる。既存の `HM_W_SOFT_VIOL`（非softをsoft上面
  へ載せる減点）と対になる位置づけだが、**そちらは軟包保護が動機で摩擦は未考慮**。
  bare floor は `on_bare_floor` 判定（`HM_W_FLOOR_VOL` と同じ機構）で除外する。

### 15.2 n=30 での初期結果（1容器族、`GH_HM_W_HARDHARD=0` vs `=25`）

| 指標 | Δ(25−0) mean | t | n |
|---|---|---|---|
| shake.n_disp_gt_2cm | **−1.17個/task** | **−2.19** | 30 |
| shake.mean_disp | −0.001m | −1.14 | 30 |
| shake.max_disp | +0.013m | +1.02 | 30 |
| fill_score | −1.04 | −1.28 | 30 |
| num_placed_items | −0.57pt | −0.52 | 30 |
| cog_score | −0.13 | −0.23 | 30 |

**解釈: v40 で学んだのと同型の境界信号。** `n_disp_gt_2cm` の t=−2.19 は閾値をわずかに
超えるが、n=30 での t≈2 は `ts25`（t=2.15@n=30→t=0.41@n=99）でも、**今回の v40 自身
（np t=+2.09@n=30→本番Public再現せず）でも偽陽性だった実績**があり、同じ危険域。
fill も非有意ながら負方向（コスト側の兆候）。**加えてこの proxy 自体が公式 stability_score
の代替として未検証**（proxyの変位減少が実際の stability_score 上昇を意味する保証がない、
mean_disp/max_disp が方向不一致なのもこの proxy の粗さを示唆する）。

**⇒ 現時点でも未提出。** 摩擦仮説の機構自体（hard-on-hard が系内最低摩擦）は運営QAに
基づく確かな根拠だが、「このレバーで実際に stability_score が上がる」ことは何一つ実測
できていない。次にやるなら: (a) 重み探索（25以外の値でproxy信号がより明確か走査）、
(b) n≥99でproxy信号自体の頑健性を先に固める、のいずれかを先行させ、
その後で初めて診断提出を検討する。

### 15.3 重み掃引（n=30、1容器族、`GH_HM_W_HARDHARD` ∈ {10,25,50,100}）

`§15.2` の t≈2 信号が本物か確かめるため、重みを振って用量反応を見た。

| weight | Δn_disp_gt_2cm | t | Δmean_disp | t | Δfill | t | Δnp(pt) | t | Δcog | t |
|---|---|---|---|---|---|---|---|---|---|---|
| 10 | −1.13 | −2.12 | −0.00088 | −1.02 | −1.14 | −1.40 | −0.73 | −0.68 | −0.21 | −0.38 |
| 25 | −1.17 | −2.19 | −0.00097 | −1.14 | −1.04 | −1.28 | −0.57 | −0.52 | −0.13 | −0.23 |
| 50 | −0.83 | −1.75 | −0.00268 | **−3.38** | −1.02 | −1.27 | +0.49 | +0.47 | +0.46 | +0.85 |
| 100 | −0.43 | −0.84 | −0.00185 | **−2.42** | −1.35 | −1.62 | +0.98 | +0.92 | +0.34 | +0.61 |

**用量反応が単調でない。** `n_disp_gt_2cm`（変位個数、離散指標）の有意性は w=10-25 で
最大（t≈−2.1〜−2.2）、w=50 で弱まり（t=−1.75）、w=100 でほぼ消える（t=−0.84）——
重みを強めるほど効果が薄れるのは「摩擦を避けるほど安定する」という機構仮説と矛盾する。
一方 `mean_disp`（連続指標）は逆に w=50 で最も強く出る（t=−3.38）。**2つの安定性指標が
別々の重みで別々に「有意」になる**のは、真の用量反応ではなく n=30 というサンプルサイズに
対して5点の重みを振ったことで生じた多重比較的な偶然（5重み×2指標=10検定中2-3件が
|t|>2）である可能性が高い。fill コストは全重みで方向は一致（−1.0〜−1.4）するが
どの点でも単独では有意でない（|t|<1.7）。

**⇒ 重み掃引はむしろ「局所信号が不安定」であることを裏付けた。** 単一重み(25)だけでの
t=2.19 を見て早合点していたら、この掃引で覆っていた（§11.2 の型と同じ構造:
直近1点の信号を検証せず一般化する誤り）。**この軸は現時点で見送りが妥当**——
mechanistically は運営QAに支えられた妥当な仮説だが、5重み×n=30=150タスク相当の
探索でも局所的に安定した効果を検出できておらず、これ以上の重み探索よりも
n≥99での再検証（同じ重み点で標本を増やす）の方が優先度が高い。ただし stability_score
自体がローカル計算不可能な以上、n≥99で proxy 信号が固まったとしても「本番でも効く」
保証にはならない点は変わらない（§15.2 と同じ限界）。

### 15.4 3つの角度からの検証 — 全て非再現・棄却

`§15.2/15.3` の t≈2 信号が本物か、3つの独立な頑健性チェックで検証した（すべて n=30）。

**A. 符号反転**（`GH_HM_W_HARDHARD=-25`、hard-on-hard を罰する代わりに**優遇**する）。
摩擦仮説が正しければ悪化するはずが、実際は改善方向（rate正規化後 t=−3.04）で、しかも
**正の重み(+25, t=−2.69)より強い**。加えて fill −2.17(t=−3.84)・np −2.4pt(t=−2.44) と
コストも正の重みより大きい。→ **符号を問わず「このスコア項を弄ると何かが変わる」だけで、
摩擦を避ける方向に特有の効果ではない。**

**B. キック強度**（0.4→0.8 m/s、family1）。0.4 で見えた `n_disp_gt_2cm` t=−2.19 が、
0.8 では **t=−0.92 まで消える**。プロトコルを変えると信号が消える＝proxy自体が
不安定であることの直接証拠。

**C. 2容器族での再現**（family1で使った `+25` を family2 へ）。`max_disp` が
**t=+3.48 で有意に悪化**（family1 とは逆方向）。§6.7「片族で改善・他族で非悪化」の
**後半（非悪化）に明確に違反**。

**rate 正規化**（`n_disp_gt_2cm / shake.n_items`、生カウントは配置数低下で見かけ改善し
得るための補正）でも A・元条件（+25）とも有意だが方向が対応しない（符号を問わず family1
でだけ動く）ことが確認され、確率的な交絡ではなく「family1 というタスク集合とこの
スコア項の組合せ固有の効果」である可能性が高い。

**⇒ 結論: この実装（`GH_HM_W_HARDHARD`、hard-on-hard 減点）は棄却する。**
3つの独立な頑健性チェック（符号・プロトコル・タスク族）のいずれも支持しなかった
——1つでも失敗すれば warning だが、3つとも失敗したのは「効果なし」の強い証拠。
摩擦仮説自体（運営QA根拠）は否定されたわけではないが、**この特定の実装・この
proxy計測では検出できなかった**。レバー自体は既定0でコードに残す（無害）。
再挑戦するなら実装を変える必要がある（例: is_soft二値ではなく実際の摩擦係数を
連続量として使う、対象をtop面だけでなく側面接触も含める、proxy自体を作り直す）。

1. **§4.1 の法則と整合する失敗**: 「効いたレバー6件は全て順序系。位置スコアの変更で

2. **構成比による構造的な避けがたさ**: 7SKU の内訳は **hard 69.1%（199/288）・

自体を否定する材料ではないが、**この構成比・このAPI（look_ahead=1で位置操作が無力）の

本番実測とSKU構成分析から導かれる暫定結論。今後この軸に戻るとすれば、順序レベルの
実装（TALL_SHIFT等と同じ「連続シフト」機構の再利用）を最後の1手として試す余地は
残るが、69%という構成比の制約は順序を変えても消えないため、期待値は低いと見る。

## 17. 発見: soft品の「登録座標」が沈降後も更新されない（構造的、公式コード側）

ユーザーの指摘（「soft品の上に別の荷物を置く際、高さ情報が変わる可能性」）を実測で
確認した。**公式コード側の構造的な挙動**であり、当エージェントのバグではないが、
局所≠本番ギャップの未解明の一因になり得る。

### 17.1 機構（`src/ground_handling/validator.py`/`env.py` を読んで確認）

`PlacementValidator.place_item()`（validator.py:178-209）は、**新しく置く荷物1個**を
warp→`settle_wait_step`物理演算→**その荷物だけ** `get_pose()` で再取得、という手順を取る。
`env.step()`（env.py:190-）もこれ以外に座標を同期する処理を呼ばない。

一方 PyBullet の `stepSimulation()` は**シーン全体**を進めるため、新しい荷物の沈降中に
**既存の荷物（特に soft、`contactStiffness`/`contactDamping` で剛性が低い）が物理的に
動きうる**。しかし `item.pos`（`get_item_info_in_containers()` が返す座標、
`build_state` が heightmap 構築に使う座標そのもの）は**その荷物が自分自身の配置時に
登録された値のまま更新されない**。

### 17.2 実測（1課題、26ステップ）

配置の直前に既配置荷物の「登録済み座標」を保存し、直後に PyBullet から**生の現在座標**を
再取得して比較した。

| ドリフトが5mm超だったイベント | 全て `is_soft=True` | 方向 |
|---|---|---|
| 6件（1課題26ステップ中） | **6/6が soft** | **全て下方向**（登録値 > 実座標） |

最大ドリフト **10.32mm**（fill の inclusion margin 5mm の**2倍**）。hard品のドリフトは
観測されなかった（全て 5mm 未満）。

### 17.3 解釈と含意

* **soft品だけが登録座標より低い位置へ沈み続ける。** 後続の荷物が上や近くに置かれる
  たびに追加で沈降している可能性が高い（`contactStiffness`/`contactDamping` による
  柔らかい接触モデルの帰結）。
* `build_state`/`ContainerHeightModel` はこの**登録座標（＝やや高すぎる）**を「既配置の
  上面」として次の候補生成に使う。soft品の上に着地させる判断は、実際より高い足場を
  前提にしている可能性がある。
* **本セッションで棄却した3つの位置レベル候補（HARDHARD/TIPRISK/BREADTH_MUL+SOFT_VIOL）
  は全て soft/hard の着地面判定に依存していた。** この座標ズレが、位置レベルの変更が
  一貫して cog/stability を予測不能に崩す一因になっている可能性がある（§16.4 の
  パターンへの1つの説明候補。ただし因果は未実証——相関を示す仮説として記録する）。
* 公式コード（`src/ground_handling/`）は変更対象外なので、この挙動自体は「直せない」。
  対応するとすれば**エージェント側で保守的なマージンを積む**（soft品の上面には
  実測ドリフト分＋安全率のクリアランスを追加で確保する）方向になる。

### 17.4 追加検証（(a) 累積性を確認、新規 `scripts/drift_diag.py`）

各配置ステップ後に**全既配置荷物**の登録座標と実座標を比較し、荷物ごとの累積ズレを
追跡するツールを新規実装した（`scripts/drift_diag.py`）。

| task | n_steps | n_placements | drift事件(>3mm) | soft/hard内訳 | 最大累積ドリフト |

| f2_0000（2容器、80品目） | 46 | 45 | 12 | **12/0** | **40.24mm** |

**(a) 確認: ドリフトは単調に累積する。** 個別荷物を追跡すると明確な増加が見える
（例: f2_0000 の item31 は 5.8mm→20.4mm→39.6mm、item77 は 4.7mm→10.3mm→21.0mm）。
**荷物寿命の長い（早期に置かれ、後から何度も上や周囲に荷物が追加される）soft品ほど
ズレが大きくなる。** 80品目族の最大ドリフト 40.24mm は fill の inclusion margin
(5mm) の**8倍**、荷物自体の厚み（soft SKUは20-40cm）の10-20%に達する規模で、
「丸め誤差」で片付けられる大きさではない。

### 17.5 n=60（両族30ずつ）での (b)(c) 検証（新規 `scripts/drift_batch.py`）

**規模を上げると (a) の傾向がさらに強まった**: 60タスク合計で drift事件 1509件、

よる誤り**だった。60タスクで見ると hard品にもドリフトが起きる
（SKU2・SKU5、計193件）が、**soft品が圧倒的多数**（1316件、87.2%）。

**(c) validator NG との相関は判定不能**: 60タスク**全て** `n_validator_ng=1`

**⇒ (a)は確定・定量化済み（n=60、mean 27.1mm・max 66.4mm）。(b)は「soft優位だが

### 17.6 (c) 連続指標での再検証 — 仮説を弱める結果

`f1_v38.jsonl`/`f2_v38.jsonl`（Phase 0、同一タスク集合・同一v38既定エージェント）を
`task_path` で突合し、ドリフト severity と fill/np/cog の相関を計算した
（再実行不要、既存結果の突合のみ）。

| | corr(ドリフト事件数, fill) | corr(ドリフト事件数, np) | corr(ドリフト事件数, cog) |
|---|---|---|---|
| family1 | +0.677 | +0.687 | +0.298 |
| family2 | +0.602 | +0.759 | +0.168 |

**全て正の相関**（負ではない）。配置数で正規化した率（`事件数/n_placements`）でも
符号は変わらない（cog: family1 +0.338 / family2 +0.188）。

**解釈: 単純な相関では仮説を支持できない。** 事件数はほぼ「配置数」の代理指標に
なっている（多く置けば土台になる soft品も増え、ドリフト事件も増える）ため、
fill/np と正相関するのは当然の交絡。cog との相関も弱いながら正（ドリフトが
多い＝悪いはずが、逆方向）。**これは v38 自身の「タスク構成による自然な分散」の中
での相関であり、§16.4 で疑ったのは「TIPRISK/BREADTH_MULがドリフトを起きやすい
配置へ誘導したか」という別の問い**（v38固定ポリシー内の相関では検証できない）。
**⇒ ドリフト仮説と cog 崩壊の直接的な結びつきは、この検証では確認できなかった
（弱められた）。** 正しく検証するには、TIPRISK/BREADTH_MUL 有効時のドリフト量を
v38 と直接比較する必要がある——それでも本番 cog_score との対応は取れない
（stability_score 同様サーバー側のみ）ため、確証には至らない可能性が高い。
現時点の結論: **17章の発見（座標の登録ズレ、最大6.6cm）自体は確定した事実**だが、
**それが v41/v42 の cog 崩壊の原因だったという主張は未実証のまま、今回むしろ
弱まった**。

### 17.7 直接比較: TIPRISK/BREADTH_MUL 有効時のドリフト量 vs v38（対応あり、n=30×4）

`drift_batch.py` に `--extra-env` を追加し、同一タスク集合で v38既定・TIPRISK有効・
BREADTH_MUL+SOFT_VIOL有効の3条件を対応比較した（§17.6の相関ではなく、実際に
提出したレバー設定そのものでの直接比較）。

| 比較 | Δmax_cum_drift_soft_mm | t | Δn_drift_events | t |
|---|---|---|---|---|
| family1: TIPRISK vs v38 | +6.93mm | +0.74 | +0.63 | +0.54 |
| family2: TIPRISK vs v38 | **+4.38mm** | **+2.72** | +0.37 | +0.29 |

**4件全てが正方向**（両レバー・両族でドリフトが v38 より悪化する方向）。

stability_score 自体がローカルで測れない以上、この仮説をこれ以上ローカルで追い込む
のは収穫逓減と判断する。§16.4 の運用規則（位置レベル変更は高リスク）は本節の結果と
矛盾しない形で独立に成立しており、**次の一手としては本仮説の深追いよりも
§16.4のルールに従い順序レベルの実験へ移る方が期待値が高い**。

## 18. `GH_HARD_MAX_RUN`（インターリーブ、HF-034）— セッション最良の局所結果

### 18.1 設計

既存の `SOFT_SHIFT`/`HEAVY_SHIFT`/`TALL_SHIFT` は全て「カテゴリ全体を連続量で前後に
ずらす」機構で、hard品の連続（＝hard-on-hard接触の起きやすい配置）自体は減らせない
（二値の hard/soft シフトは SOFT_SHIFT と数学的に重複するため試す価値が薄いと判断、
§15.6/17.7 での位置レベル敗退を踏まえた再設計）。

`_interleave_hard_order`（agent.py、`_post` パイプラインの最終段）は構造的に異なる
操作を行う: **hard品が `GH_HARD_MAX_RUN` 個連続したら、残りの列から直近のsoft品を
1個前へ引き出す**。pending から pop して result へ append するだけなので「全index
を過不足なく1回」の契約は自動的に保たれる。既定 0（無効、v38恒等）。

### 18.2 n=30×2 族での結果（`GH_HARD_MAX_RUN=2`）

| Δcog | +0.52（t=+1.33、改善方向） | −0.62（t=−2.48、絶対値小） |

**セッション最良の局所結果**。family2 で fill・np が明確に有意に改善（t=3.14/5.02）。
cog は family2 で統計的に有意な下落（t=−2.48）だが**絶対値はわずか−0.62**——
§11条件2の危険閾値（−3超）を大きく下回る安全域で、v41(−3.90)/v42(−5.42)とは
性質が異なる。family1 は全指標非有意ながら**方向は全て非負**（cogはむしろ改善）。
§11.1「Δfill>0 かつ Δnp>0 かつ soft非悪化 かつ ctrガード」、§6.7「片族で有意改善・
他族で非悪化」の両方を、本セッション中で初めて満たす候補になった。

### 18.3 診断提出 v43

package_submit → 直後に復元（テスト再パス確認）。

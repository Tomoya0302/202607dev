## 1. コーディングエージェント運用ルール

### 1.1 基本フロー（1タスク＝1チケット＝1検収）

1. 人間が §6 のチケット表から**依存が満たされたチケットを1件**選ぶ
2. 付録Aのテンプレートに「チケットID・本書の該当節・対象ファイル」を埋めてエージェントに投入する。**本書の該当節と対象ファイルの現状以外は渡さない**（コンテキストを絞るほど弱いモデルは安定する）
3. エージェントが実装し、指定の DoD コマンドを自分で実行して全緑まで修正する
4. 人間が DoD コマンドを**再実行して検収**し、付録Bのチェックリストを通してからコミットする（1チケット=1コミット）
5. 不一致・疑問があればエージェントは**実装せずに**付録Dの形式で質問を返す（勝手な解釈で先に進ませない）

### 1.2 エージェントに渡すコンテキストの最小構成

* 本書の該当節（§4.x など該当モジュールの節**のみ**）
* §2（グローバル規約）と §3（データ構造）— 毎回添付する固定コンテキスト
* 対象ファイルの現在の全文（新規なら「新規」と明記）
* 該当テストファイルの全文（テストは人間側の資産。§1.3 参照）
* 依存モジュールは**公開APIのシグネチャのみ**（実装本文は渡さない）

### 1.3 禁止事項（エージェント側の絶対ルール）

1. **仕様の再解釈・独自設計の禁止**：本書の擬似コード・シグネチャ・定数名をそのまま実装する。改善案があっても実装せず質問として報告する
2. **`src/ground_handling/`（公式コード）の変更禁止**。読み取り・importは可
3. **`tests/` の変更禁止**（チケットが明示的にテスト作成・修正を指示する場合のみ可）
4. **新規依存の追加禁止**：`src/packing_core/` は numpy と標準ライブラリのみ。`training/` は torch / sklearn / cma を追加可（チケットに明記された場合のみ）
5. **数値リテラルのハードコード禁止**：寸法・マージン・重み・閾値・台数はすべて `constants.py` 経由（§3.5）
6. **公式コードのコピーは L字経路判定関連チケット（T-016A／T-016B）のみ許可**。T-016A は公式 `PlacementValidator.check_transport_path` を**無改変のまま**参照オラクルとして呼び出す（コピーではなく import・実行）。T-016B で公式の数式・定数を転記した箇所には出典（ファイル名・クラス名・関数名）をコメントで必須記載（詳細は §4.5・§6）
7. `print` デバッグ禁止（`logging` のみ）。`time.time()` 禁止（`time.monotonic()` のみ）
8. fixtures（`datasets/fixtures/`）の手動編集禁止（生成スクリプト経由のみ）

### 1.4 出力形式

* 変更はファイル全文で提出（部分diffは事故のもと）。複数ファイルの場合はファイルごとに区切る
* 末尾に必ず：変更ファイル一覧／実行したテストコマンドと結果／仕様と異なる判断をした箇所（**原則「なし」**。ある場合は付録D形式）

## 2. グローバル実装規約

### 2.1 言語・依存

* Python は評価基盤に合わせる（仮定 A3/Q3 の回答待ち。確定まで **3.10 互換構文**で書く：`match` 文禁止、`X | None` は可）
* `src/packing_core/`：**numpy＋標準ライブラリのみ**（scipy・torch・numba 禁止。提出物に入るため）
* `training/`・`scripts/`：torch / sklearn / cma / pandas 可（チケット指定時）

### 2.2 スタイル

* 全公開関数に型ヒント必須。データの受け渡しは §3 の dataclass か `np.ndarray`（shape・dtype を docstring に明記）
* docstring は1行要約＋`Args:`／`Returns:`／`Raises:`（Google style）
* 命名：`snake_case`。座標変数は必ず接尾辞で系を明示：`pos_world` / `pos_rel`（裸の `pos` 禁止）
* 純関数を基本とし、可変グローバル状態禁止。`dataclass(frozen=True)` を既定とする（可変が必要な場合のみ通常dataclass）
* ソートは必ず `key=` を明示（dict の挿入順・浮動小数の同値順に依存しない）

### 2.3 数値規約

* 単位は m / kg / s に統一。度・cm・mm を内部で使わない（定数定義時にコメントで換算を書くのは可）
* 内部計算は float64、**エージェント出力（`place_pos`）のみ float32**（§3.4 の `make_action` が唯一の変換点）
* 幾何比較の許容誤差は `constants.EPS_GEOM = 1e-9`（同一判定）と `constants.TOL_CONTACT = 5e-3`（接触判定 5mm）の2種のみ。関数ローカルに独自 eps を定義しない
* 乱数は `np.random.default_rng(seed)` を引数注入。モジュール内で `np.random.seed` を呼ばない

### 2.4 例外・ログ・時間

* `packing_core` 内の関数は「不正入力→`ValueError`」を投げてよい。**ただし `agent.py` の `policy()` は例外を外に漏らさない**（watchdog が全捕捉、§4.12）
* ログは `logging.getLogger("packing")` 配下。1ステップの計測値は telemetry（§4.13）に集約し、ログには要約のみ
* 時間計測は `time.monotonic()`。締切は `StepBudget`（§4.11）経由でのみ扱う

## 3. 共通データ構造と座標規約（毎タスク添付する固定仕様）

### 3.1 座標系

* Z-up 右手系。X=幅、Y=奥行、Z=高さ。**開口部は Y マイナス側**（荷物は y が小さい側から入る。奥＝y が大きい側）
* コンテナ i の原点の世界座標は `origin_world(i) = (offset_x_i, 0, 0)`、`offset_x_i = container_list[i]["center"][0]`（公式 `containers.py::local_to_global` が生成した X オフセット。`spacing` は agent I/F の `init_states`/`observation` に存在しないため使用しない。`index * spacing` の再計算や `center.x` からの spacing 逆算も行わない。根拠は `interface_notes.md` §I-8）
* 変換（`state.py` に集約。他モジュールでの直書き禁止）：

  * `pos_rel = pos_world - origin_world(i)`
  * `pos_world = pos_rel + origin_world(i)`
* `place_pos` は**荷物の中心**のコンテナ相対座標（仮定 A10：`packed_items` の `pos` も幾何中心。Phase 0 で要確認）

### 3.2 orientation テーブル（仮説→T-003 で公式実装と突合）

入力寸法を `(L, W, H)` とし、`oriented_size(size, o)` は以下を返す。**この表は README 記述からの導出仮説（仮定 A13）**。T-003 の突合で不一致が出たら、本表を修正してから実装を直す。

| o | 意味        | 返り値       | 例 size=(0.5, 0.4, 0.3) |
| - | --------- | --------- | ---------------------- |
| 0 | そのまま      | (L, W, H) | (0.5, 0.4, 0.3)        |
| 1 | X軸90°     | (L, H, W) | (0.5, 0.3, 0.4)        |
| 2 | Y軸90°     | (H, W, L) | (0.3, 0.4, 0.5)        |
| 3 | Z軸90°     | (W, L, H) | (0.4, 0.5, 0.3)        |
| 4 | Y90°→Z90° | (W, H, L) | (0.4, 0.3, 0.5)        |
| 5 | X90°→Z90° | (H, L, W) | (0.3, 0.5, 0.4)        |

### 3.3 dataclass 定義（`packing_core/types.py`、T-001）

```python
from dataclasses import dataclass, field
import numpy as np

Vec3 = np.ndarray  # shape (3,), float64

@dataclass(frozen=True)
class ItemSpec:
    idx: int              # プール内 index（仮定 A11: policyのitem_idxはこの値）
    size: Vec3            # 回転前 (L, W, H) [m]
    weight: float         # [kg]
    kind: str | None       # T-012確定：公式 observation に kind 相当キーは存在しない
                           # （interface_notes.md §H）。build_state が observation から
                           # 構築する場合は常に None。item_params.xlsx 由来の種別キーは
                           # 学習データ合成側でのみ付与され得るが、公式 observation を
                           # 入力とする提出時推論では利用可能とは仮定しない。
                           # 提出時のランタイム方策は kind に依存してはならず、種別に
                           # 相当する特徴量は is_soft/is_priority を使う。is_soft は
                           # 非単射（suitcase 3種=False、duffel/cardboard/backpack/
                           # daypack=True）のため kind へ逆算できない。
                           # kind と is_soft は別概念であり同義ではない。
    is_soft: bool         # 種別→bool 変換は constants.KIND_IS_SOFT
    is_priority: bool

@dataclass(frozen=True)
class PlacedItem:
    pos_world: Vec3       # 幾何中心・世界座標（仮定 A10）
    orn_quat: np.ndarray  # shape (4,), PyBullet順 (x,y,z,w)（仮定 A9）
    size: Vec3            # 回転前寸法
    weight: float
    is_soft: bool
    is_priority: bool
    aabb_min_rel: Vec3    # 回転後AABB（コンテナ相対）: state.py が計算して充填
    aabb_max_rel: Vec3

@dataclass(frozen=True)
class EMSBox:
    min_rel: Vec3
    max_rel: Vec3
    def size(self) -> Vec3: ...
    def volume(self) -> float: ...

@dataclass
class Candidate:
    item_idx: int
    container_idx: int
    ems_id: int
    orientation: int
    pos_rel: Vec3          # 配置中心（コンテナ相対）
    osize: Vec3            # 回転後寸法
    feasible: bool = False
    reject_reason: str = ""     # "dims"|"inclusion"|"overlap"|"ceiling"|"path"|""
    features: dict = field(default_factory=dict)  # §4.8 の特徴量
    score: float = 0.0
    p_success: float = 1.0
```

**アルゴリズム要点**

* `cdict` のキー名（`cut_x`/`cut_y`/棚/`thickness`/`n_vecs`/`points`/`center`/`volume`）は `interface_notes.md` の転記表（＝`constants.OBS_KEYS["container"]`）に従う。**キー名をこの仕様書から推測しない**（T-006 投入時に転記表を添付する）
* **`buffer` は `cdict` に存在しないキー**（`Container.buffer` はconfigで上書き可能な内部属性であり、observation には転記されない。T-006 で確認済み、`interface_notes.md` §I-7 参照）。固定値で補ってはならない。必要な場合は公式実装の関係式
  `buffer = float(cdict["center"][2]) - float(cdict["height"]) / 2.0` から都度復元する。
* **`offset_x`（コンテナ原点世界X）は `float(cdict["center"][0])` を直接使用する**。`spacing` は agent I/F
  （`init_states`/`observation`）に存在しないため、`index * spacing` の再計算や `center.x` からの
  spacing 逆算は行わない。公式 `containers.py:61,66,238–240` により `center[0] == offset_x` が成り立つ
  （`local_to_global((0,0,hz+buffer))` の X 成分）。詳細は `interface_notes.md` §I-8 参照。
* コンテナの内壁形状（`inner_min_rel`/`inner_max_rel`/`cut_planes`）は、`thickness`/`buffer` からの寸法式で再構築するのではなく、公式包含判定と同じ `cdict["points"]`（世界座標の代表点）と `cdict["n_vecs"]`（外向き単位法線）を正として復元する：

  ```python
  origin_world = np.array([float(cdict["center"][0]), 0.0, 0.0], dtype=np.float64)
  point_rel = np.asarray(point_world, dtype=np.float64) - origin_world
  normal_rel = np.asarray(normal_world, dtype=np.float64)
  d = np.dot(normal_rel, point_rel)
  # 有効空間の半空間: normal_rel · x <= d
  ```

  cut なし（軸整列面のみ）の場合、6面の半空間から `inner_min_rel`/`inner_max_rel` がそのまま定まり、`cut_planes = []` となる。
* `floor_z[i,j]`：セル中心 (x,y) で cut_planes を z について解いた床高さの max。`ceil_z` は内壁上面と棚下面の min
* 格子は**絞り込み・支持率・height 用**。包含・非重複の最終判定に使わない（§2規約）
* `effective_volume(space)` は格子積分（cell³ 近似）で実装する。**責務は `floor_z`/`ceil_z` による
  単一区間格子表現上の近似・診断用体積を返すことであり、公式fillスコアの分母ではない**（正式な
  fill分母は `evaluator.py` または転記済みの公式値を正とする）。`cdict["volume"]`をそのまま返しては
  ならない。DoDの詳細（直方体基準ケースと cut・棚ケースの扱いの違い）は下記T-007節を参照。

**T-007：cut・棚の変換規則**（読解一次情報・詳細式は `interface_notes.md` §K）

* `cut_planes` の floor_z/ceil_z への反映：セル中心 `(x_c,y_c)` に対し各平面 `(normal_rel=(nx,ny,nz), d)` を
  `normal·(x_c,y_c,z) <= d` について `z` で解く。`nz < -EPS_GEOM` なら下限 `z >= (d-nx*x_c-ny*y_c)/nz` を
  `floor_z` 候補（`inner_min_rel[2]` と `max`）、`nz > +EPS_GEOM` なら上限を `ceil_z` 候補
  （`inner_max_rel[2]` と `min`）とする。`|nz| <= EPS_GEOM` の面は z を拘束しないため
  floor_z/ceil_z の算出には寄与させない（格子は絞り込み専用のため、この種のXY制約は
  `contains_oriented_box` の半空間判定でのみ最終判定する）。
* **セル中心座標・格子添字の規約**（T-006実装 `nx = max(1, round(size[0]/cell))` /
  `ny = max(1, round(size[1]/cell))`（`size = inner_max_rel - inner_min_rel`）をそのまま正式仕様と
  する。変更不要）：
  ```python
  x_c[i] = inner_min_rel[0] + (i + 0.5) * cell   # i = 0, ..., nx-1
  y_c[j] = inner_min_rel[1] + (j + 0.5) * cell   # j = 0, ..., ny-1
  ```
  有効index範囲は `i∈{0,...,nx-1}`, `j∈{0,...,ny-1}`。端数セル（`round()`により`nx*cell`が
  `size[0]`と厳密一致しない場合、最大`cell/2`の差）について、`effective_volume()`は全セルを
  `cell×cell`として扱い面積補正は行わない（T-006既存実装のまま）。`nx=round(size/cell)`の定義
  （`|nx-size/cell|<=0.5`）から `x_c[nx-1] <= inner_max_rel[0]` が常に成り立つため（Y軸も同様）、
  セル中心が内壁境界を超えることはなく、クランプ処理は不要（証明は `interface_notes.md` §K.7参照）。
* 小棚（`_create_small_shelf` 相当）・大棚（`_create_shelf` 相当）のAABBは、公式コードの
  `halfExtents`/`position` 式（`interface_notes.md` §K.2/K.3）をコンテナ相対座標へ変換して求める。
  **小棚は `cdict["shelf"]` の真偽・`cut_planes` の有無にかかわらず常に計算する**（公式コード上、
  `require_shelf` の分岐によらず無条件生成されるため）。**大棚は `cdict["shelf"] is True` の
  ときのみ計算する**。生成条件を `cut_planes` の有無で判定してはならない（`cut_planes` は
  半空間分類上の非軸整列面リストに過ぎず、cut形状の存在を表す正式なフラグではないため）。
* 算出したAABBは `inner_min_rel`/`inner_max_rel` で軸ごとにクリップ（`elementwise_max`/`min`）した上で、
  クリップ後の全軸長が `EPS_GEOM` を超える場合のみ `shelf_boxes` に追加する（ゼロ・負寸法は追加しない）。
  クリップが必要な理由：大棚のX半径 `length/2-thickness/2` は内壁AABBのX境界より壁厚半分だけ外側に
  出るため（`interface_notes.md` §K.4）。
* `contains_oriented_box` は上記に加え、cut・棚を含む拡張として (1) 内壁AABBチェック、
  (2) 箱の8頂点すべてが全 `cut_planes` の半空間を満たすことの確認、(3) 箱AABBが `shelf_boxes` の
  いずれとも交差しないことの確認、を行う。
* 既存 `tests/test_container_space.py` の合成fixtureは `cut_x=0.3`/`cut_y=0.3` を保持したまま
  cutなし直方体を意図しており、上記の小棚無条件生成則と矛盾する。この矛盾は fixture 側の
  不整合として扱い、T-007のテスト準備セッションで `cut_x=0.0, cut_y=0.0` に修正する
  （`container_space.py` にfixture救済分岐は追加しない。`interface_notes.md` §K.5）。
* golden fixture は `ground_handling/utils.py::write_open_cut_corner_cup_obj`（PyBullet非依存の
  純関数）を固定パラメータで直接呼び出して `points`/`n_vecs` を取得し、期待 `floor_z`/`ceil_z`/
  shelf AABB は `container_space.py` を経由しない独立計算で求める（`interface_notes.md` §K.9）。
* `effective_volume(space)` の責務とDoD（cut・棚を含む場合の扱いを再定義。実測調査の結果、
  棚上方空間の喪失により `cdict["volume"]` との<1%一致は構造的に達成不可能と判明したため）：
  - **責務**: `floor_z`/`ceil_z` による単一区間格子表現上の近似・診断用体積を返す関数と位置づける。
    公式fillスコアの分母には使用しない。fill分母は `evaluator.py`（または転記済みの公式値）を
    正とする、既存の docstring 方針（本節冒頭）を維持・強化する。
  - **DoD①（直方体基準ケース）**: `cut_x=0`・`cut_y=0`・小棚がクリップ後ゼロ体積・`shelf=False`・
    `cut_planes` なしの場合、解析的な内壁体積との相対誤差 <1% を維持する。
  - **DoD②（cut・棚を含むケース）**: `cdict["volume"]` との一致は求めない。golden の
    `floor_z`/`ceil_z` から独立計算した格子積分値
    （`sum(max(ceil_z-floor_z, 0) * cell * cell)`。全セルを `cell × cell` として扱う現行実装の
    仕様に合わせ、境界セルの特別扱いはしない）と一致することを検証する。比較は
    `np.testing.assert_allclose(actual, expected, rtol=0.0, atol=EPS_GEOM)` を原則とする。
    浮動小数演算順序により `EPS_GEOM` で不安定な場合は、恣意的に許容値を広げず実測値を報告して
    停止する。
  - **DoD③（公式体積との差、診断値）**: `effective_volume` と `cdict["volume"]` の絶対差・相対差は
    テスト出力またはコメントに記録するが、合否条件にはしない。
  - **既知の近似誤差**（本チケットで実測済み。固定fixture: `length=height=width=1.00`,
    `thickness=0.02`, `cut_x=cut_y=0.20`, `buffer=0.02`, `shelf=False`。詳細は
    `interface_notes.md` §K.10）：
    - cut床上昇のみ反映: 対公式体積式で相対誤差 約2.37%
    - cut床上昇＋小棚ceilキャップ反映: 対公式体積式で相対誤差 約8.28%
    - 棚ceilキャップによる上方空間の喪失体積: 約0.09216 m³（公式体積の約10.65%）
    これらは記録用の実測値であり、**本番コード（`container_space.py`）へ数値としてハードコード
    しない**。
  - **`effective_volume()` の docstring に明記する事項**（実装セッションで反映）：
    1. 格子表現（`floor_z`/`ceil_z`の単一区間）上の近似体積であること
    2. 棚のあるセルでは `ceil_z` を棚下面に設定するため、棚上方空間を保守的に無視すること
    3. cut形状では、格子離散化と公式体積式の形状定義差（`interface_notes.md` §K.10）により
       誤差が生じること
    4. fillスコアの分母には使用しないこと。fill分母は `evaluator` 由来の公式値を正とすること
    5. 包含の最終判定は `contains_oriented_box()` の連続幾何を使用すること
  - **既知の制約（スコープ外）**: 棚上方空間を単一区間の `floor_z`/`ceil_z` で表現できない点は、

**T-008：`cells_of_aabb`・`bake_placed` の変換規則**

* **セル帰属規約（半開区間・セル中心代表）**：格子中心座標は `_build_floor_ceil`（T-006/T-007）と
  完全に同じ生成式を使う（別の座標計算規約を新設しない）。

  ```python
  x_center[i] = space.inner_min_rel[0] + (i + 0.5) * space.cell   # i = 0, ..., nx-1
  y_center[j] = space.inner_min_rel[1] + (j + 0.5) * space.cell   # j = 0, ..., ny-1
  ```

  AABB（`bmin`, `bmax`）の各軸について、セル中心が次の半開区間に入るセルを選択する。

  ```text
  bmin <= cell_center < bmax   # 下端は含む、上端は含まない
  ```

  したがって、2つのAABBが同一平面で面接触し、その境界がちょうどセル中心と一致する場合、
  境界セルは上側（`bmax`側）のAABBにのみ帰属し、下側（`bmin`側）のAABBには帰属しない
  （重複帰属しない）。NumPy実装では、格子中心列に対する `np.searchsorted` と等価にする。

  ```python
  start = np.searchsorted(centers, clipped_min, side="left")
  stop = np.searchsorted(centers, clipped_max, side="left")
  ```

* **clamp規約**：まずXY範囲をコンテナ内壁のXY範囲と交差させる。

  ```python
  clipped_min = np.maximum(bmin[:2], space.inner_min_rel[:2])
  clipped_max = np.minimum(bmax[:2], space.inner_max_rel[:2])
  ```

  インデックスは最終的に `X: [0, space.height.shape[0]]`・`Y: [0, space.height.shape[1]]` の
  範囲へ収める。`EPS_GEOM` によるセル占有範囲の外側拡張は行わない。

  入力検証：`bmin`/`bmax` は shape `(3,)`・全要素有限値であることを要求し、いずれかの軸で
  `bmax < bmin - EPS_GEOM` となる場合は `ValueError` とする。clamp後にXY面積が正でない場合は
  空範囲（後述）を返す。

* **空範囲の表現**：AABBがコンテナXY領域と交差しない、またはclamp後に正のXY面積を持たない場合は、
  必ず次のcanonical形を返す（片方の軸だけ実範囲を残した空sliceにしない）。

  ```python
  (slice(0, 0), slice(0, 0))
  ```

* **`bake_placed(space, placed: list[PlacedItem]) -> None`**：呼び出しのたびに `height` を
  全再構築する（前回の `height` を引き継がない。増分キャッシュは実装しない）。

  1. `space.height[...] = space.floor_z` で初期化する（各セルの有効床高さ）。
  2. 各 `PlacedItem` について、`aabb_min_rel`/`aabb_max_rel` をそのまま（回転AABBの再計算はせず）
     `cells_of_aabb` へ渡す。
  3. 返り値が空slice（`(slice(0,0), slice(0,0))`）ならその荷物をスキップする。
  4. 対象セルを次で更新する（現在値と `aabb_max_rel[2]` の max を保持。`ceil_z` によるclampはしない）。

     ```python
     space.height[x_slice, y_slice] = np.maximum(
         space.height[x_slice, y_slice],
         placed_item.aabb_max_rel[2],
     )
     ```

  5. `floor_z`/`ceil_z` は変更しない。

* **性能予算**：`bake_placed`（80個）<80ms/台（既存記載を維持）。

* **T-008テスト**（`tests/test_container_space.py` へ追記想定。以下の観点を最低限含める）：

  1. 空の `placed` で `height == floor_z`
  2. 1個のAABBが想定したセル中心範囲だけを更新する
  3. 上端境界（`bmax`）がセル中心と一致した場合、そのセルを含まない
  4. 下端境界（`bmin`）がセル中心と一致した場合、そのセルを含む
  5. 内壁外へ一部はみ出すAABBがclampされる
  6. 完全に範囲外のAABBがcanonicalな空slice（`(slice(0,0), slice(0,0))`）を返す
  7. 複数AABBが同じセルを覆う場合、最大の top-z を保持する
  8. 同じ `placed` で2回 `bake_placed` を呼んでも同じ結果になる（べき等性）
  9. 2回目の呼び出しで荷物を減らすと、古い `height` が残らない（全再構築の確認）
  10. `bake_placed` 呼び出し前後で `floor_z`/`ceil_z` が変更されない
  11. 80個の `PlacedItem` で性能予算（<80ms/台）を満たす

**T-016B: L字経路用派生フィールド**（A15確定、2026-07-19。詳細分析・実測根拠は

`build_container_space` 実行時に、公式L字経路式（A12・`validator.py::check_transport_path`）から

| --- | --- | --- | --- | --- | --- | --- | --- |

**設計根拠**（実測で確認済み。数値検証は`docs/interface_notes.md` §L参照）：

* 公式4値（`resting_surfaces`/`ceiling_surfaces`各2値）のうち2値は既存`inner_min_rel[2]`
  （`==thickness`）・`inner_max_rel[2]`（`==height+buffer-thickness`）と恒等的に一致するため、
  新規フィールドは**残り2値のみ**（`path_mid_resting_z_rel`/`path_mid_ceiling_z_rel`）で足りる。
  天井cap（`rel_z`の上限）も同様に`inner_max_rel[2]`のみから合成可能で新規フィールド不要
  （`z_cap = inner_max_rel[2] - half_z - pp.start_margin`）。
* 経路障害物には**raw AABB（クリップ前）が必須**。既存`shelf_boxes`（クリップ後）は公式PyBullet
  bodyより小さく、片側安全性（`proxy_pass ⇒ official_pass`）を式で証明できないため使用しない
  （壁・cut・天井は公式経路判定の直接衝突対象ではないため、独自障害物は追加しない）。
* `_container_geometry_key`（`state.py`、増分キャッシュの有効性判定キー）は、`height`/`buffer`の
  個別値が既存キー要素（`inner_min_rel`/`inner_max_rel`/クリップ後`shelf_boxes`/`cut_planes`）から
  一般に一意復元できることを証明できなかった（クリップ後`shelf_boxes`が退化・空集合になり得る
  edge caseが存在し、その場合`height`と`buffer`の分離情報が失われるため）。安全側の最小修正として、
  上記6フィールドを`_container_geometry_key`の対象コンテナ部分へ直接追加する
  （間接的な復元可能性に依拠しない）。

### 4.3 `ems.py` — 空き空間候補（T-009〜T-011）

**目的**：EMS（Empty Maximal Space）の全再構築・差分更新・正規化記述子。

**公開API**

```python
def generate_ems(space: ContainerSpace,
                 placed_aabbs: list[tuple[Vec3, Vec3]]) -> list[EMSBox]
    # 全再構築：有効空間AABBから開始し、障害物（placed + shelf）ごとに update_ems を適用
def update_ems(ems_list: list[EMSBox], obstacle: tuple[Vec3, Vec3],
               space: ContainerSpace) -> list[EMSBox]
    # 差分更新：
    #   for ems in ems_list:
    #       if not intersects(ems, obstacle): keep
    #       else: obstacle の6面それぞれで ems を切断した6個の部分箱のうち
    #             体積>0 のものを追加
    #   その後 remove_contained → prune_min_dim
def remove_contained(ems_list) -> list[EMSBox]      # 他に完全内包されるEMSを除去
def prune_min_dim(ems_list, min_dim: Vec3) -> list[EMSBox]
def select_topn(ems_list, n_per_container: int) -> tuple[list[EMSBox], float]
    # z1昇順→体積降順で上位N。戻り値2つ目は打切り率（捨てた「min_dim を満たすEMS」数/全数）
def normalize_descriptors(ems_list, space) -> np.ndarray  # shape (N,6), [0,1]
    # (x1,y1,z1,x2,y2,z2) を各軸で (v - inner_min)/(inner_max - inner_min)
```

**6面切断の定義**（obstacle=(omin,omax)、ems=(emin,emax)）：

```
sub1: emax.x → omin.x   （x < omin.x 側）    sub2: emin.x → omax.x（x > omax.x 側）
sub3/4: y について同様    sub5/6: z について同様
各 sub は他軸の範囲を ems のまま維持する
```

**T-011 決定事項（境界条件・タイブレーク。人間承認 2026-07-17）**

* `select_topn` の決定的ソートキー（辞書式昇順）：

  ```python
  (
      float(ems.min_rel[2]),
      -float(ems.volume()),
      float(ems.min_rel[0]),
      float(ems.min_rel[1]),
      float(ems.max_rel[0]),
      float(ems.max_rel[1]),
      float(ems.max_rel[2]),
  )
  ```

  すなわち `min_z` 昇順→体積降順→`min_x`→`min_y`→`max_x`→`max_y`→`max_z` の順。入力順や
  Python の安定ソートだけには依存しない。

* `select_topn` の `n_per_container` 境界値：

  * `n_per_container < 0` → `ValueError`
  * `n_per_container == 0` かつ入力が非空 → `([], 1.0)`
  * `n_per_container == 0` かつ入力も空 → `([], 0.0)`
  * `n_per_container >= len(ems_list)` → 全件をソートして返し、打切り率 `0.0`

* 打切り率の定義：`discarded_count / valid_ems_count`（`valid_ems_count` は `select_topn` へ
  渡された有効EMS数）。入力が空で分母が0の場合は `0.0`。

* `prune_min_dim`：各EMSの3軸寸法が対応する `min_dim` **以上**の場合だけ残す（1軸でも不足すれば
  除外、境界値と等しい場合は残す）。出力は入力順を維持し、入力リスト・EMS内部配列を変更しない。

* `normalize_descriptors`：座標順は `(min_x, min_y, min_z, max_x, max_y, max_z)`。各軸を
  `inner_min_rel`／`inner_max_rel` で独立に正規化する。戻り値は shape `(N, 6)`・dtype
  `float64`（空入力は shape `(0, 6)` の `float64` 配列）。内壁幅（`inner_max_rel - inner_min_rel`）
  のいずれかの軸が `EPS_GEOM` 以下の場合は `ValueError`（`np.clip` 等で0除算・仕様不整合を
  隠さない）。入力EMS・`ContainerSpace` は変更しない。

**性能予算**：`update_ems` <10ms/配置、`generate_ems`（80障害物）<200ms/台。

**テスト**

* 空コンテナ（cut なし、内壁 1.5×2.0×1.6）→ EMS 1個＝内壁全体
* 上記に 0.5³ の箱を FLB 角 `(min+size/2)` に配置 → EMS ちょうど3個：`x∈[0.5,1.5]` 全yz／`y∈[0.5,2.0]` 全xz／`z∈[0.5,1.6]` 全xy（座標は inner_min 原点で表記、許容 1e-6）
* 性質テスト（ランダム10配置×20シード）：`generate_ems`（全再構築）と `update_ems` 逐次適用の結果集合が一致（各EMSを 1e-6 で丸めた tuple 集合として比較）。remove_contained 後に相互内包ゼロ

### 4.4 `state.py` — 観測→内部状態（ステートレス再構築）（T-012〜T-013）

**目的**：毎ステップ observation から状態を**ゼロから**組み立てる。世界↔相対変換と `make_action` の唯一の置き場所。

**公開API**

```python
@dataclass
```

**辞書契約（T-012確定）**：`placed`/`ems`/`ems_truncation` はいずれも、observation の
`container_list` に含まれる**全コンテナ index** をキーとして持つ（配置・EMSが空でもキー自体は必須）。
既配置がないコンテナは `placed[idx] == []`。EMSが1件も残らない状況は通常想定しないが、
`ems[idx]` は**空リストで代用せず**、必ずそのコンテナの有効空間（`inner_min_rel`/`inner_max_rel`・
`shelf_boxes` 反映済み）から `generate_ems`/`select_topn` を実行した結果を格納する。cut・棚なしの
直方体コンテナで既配置0件なら `generate_ems` は内壁AABBに一致する EMS 1個を返し、
`select_topn` は打切りなし（`valid_count=1 <= n`）のため `ems_truncation[idx] == 0.0` になる。

**meta 契約（T-012確定）**：`meta` は少なくとも `optimize`・`lookahead_k` の2キーを含む（値は
`observation`/`init` の同名フィールドと一致）。追加キーは許容するが、`spacing` は agent I/F に
存在しないため含めない（§3.1・interface_notes.md §I-8）。

**性能予算**：`build_state` 全体 ≤500ms（6台・既配置80個。手順書 Phase 1 DoD と同値）。

**増分キャッシュ（T-013／`build_state_cached`）**：`build_state` は全再構築の唯一の正として
**不変**のまま維持する。高速化のため隣に次を新設する（可変グローバル状態・永続 `ContainerSpace`

- **AABB署名（キャッシュ有効性判定専用。丸めない）**：
  `tuple(float(v) for v in (*aabb_min_rel, *aabb_max_rel))`（6要素。`round()` は使わない厳密値）。

  canonicalな `height` 変化を見逃し得るため）。丸め比較は `test_state_rebuild.py` 側のEMS
  等価性テスト（§4.3と同じ丸め）にのみ用いる。
- **geometry_key（キャッシュ有効性判定専用。丸めない・グローバル／コンテナ単位の2階層）**：

  ```python
  geometry_key = (
      global_settings_key,                              # 全コンテナ共通設定
                                                          # （StageParams().ems_top_n_per_container
                                                          #  など、再構築結果へ影響する設定）
      tuple(container_geometry_key for each container),  # コンテナ列挙順。各要素は
                                                          # (offset_x, inner_min_rel, inner_max_rel,
                                                          #  cell, shelf_boxes, cut_planes) を
                                                          # 丸めない float64 値としてtuple化したもの
  )
  ```

  数値は丸めない（`round()` を使わない厳密値）。判定は次の2段階：
  `global_settings_key` が現在と不一致なら**全コンテナ**を無効化（全再構築）する。
  `container_geometry_key` が現在と不一致なコンテナは**そのコンテナだけ**無効化し、他の
  コンテナのヒット判定には影響しない（下記「無効化はコンテナ単位」の原則をこの階層構造で
  直接満たす）。
- **ヒット条件（コンテナ単位。以下を全て満たす場合のみ増分更新を行う）**：
  (1) `cache is not None`、(2) `global_settings_key` が現在と一致し、かつ当該コンテナの
  `container_geometry_key` が現在と一致（いずれも丸めない値での厳密一致）、(3) 前回の
  `placed_signatures[idx]` が現在の署名集合に多重集合として包含される、(4) 差分が追加のみ
  （削除・置換ではない）、(5) 既配置AABBに変化がない（=(3)(4)の帰結。1e-6未満の位置変化を
  含め、署名が完全一致しない変化はすべて物理沈降ドリフト等として検出する）、(6) 当該 `idx` の
  `heights`/`ems_full`/署名がキャッシュに揃っている、(7) 判定に曖昧さがない。差分が空集合なら
  該当コンテナはキャッシュの結果をそのまま（コピーして）再利用する。差分がある場合は追加された
  `PlacedItem` のみを対象に、height は `cache_bake_placed`（§4.2）、EMSは既存の `update_ems` を
  順に適用して更新する（新規のEMS用関数は追加しない）。
- **無効化条件（該当コンテナのみ全再構築へフォールバック）**：コンテナ形状・再構築設定の変更
  （`global_settings_key`/`container_geometry_key` 不一致）、既配置の削除・移動・回転・所属変更、
  配置数の減少、1e-6未満の位置変化を含む既配置AABBの変化、非有限値・不正な署名、キャッシュ内容
  の欠損、判定不能——のいずれかを**検出可能な条件として明示的に判定**した場合に限り、当該
  コンテナを全再構築へフォールバックする。**キャッシュが有効であることを確認できない場合は
  必ず全再構築へフォールバックする**（キャッシュのために正しさを犠牲にしない）。無効化は
  コンテナ単位で判定し、他のコンテナのヒット判定には影響しない。**想定外の例外・実装バグ
  （`cache_bake_placed`/`update_ems` 等の増分プリミティブ呼び出し中に発生するものを含む）は、
  上記の検出可能なキャッシュミス条件と同列に扱って握りつぶしてはならない**。それらは伝播させ、
  呼び出し元（テスト）で失敗として顕在化させる（`build_state_cached` 内で広範な
  `except Exception` を用いて全再構築へ読み替えてはならない。例外を外に漏らさない
  `Agent.policy()` の方針、§2.4・§4.11 とは別レイヤーの話であり、本関数はその対象外）。
- **複数追加の扱い**：1回の呼び出しで複数件が新規追加された場合、EMS更新が追加順に依存
  しないことを `test_state_rebuild.py` で検証する。順序非依存を保証できないことが判明した
  場合は、増分ヒットの条件を「1回の呼び出しにつき追加は最大1件」に限定する（複数追加時は
  無条件で全再構築へフォールバックする）よう本節と実装を改める。
- **不変性**：`StateCache` は `frozen=True`。`heights` はコピー＋`writeable=False`、`ems_full`
  は `tuple` で、各要素 `EMSBox` の `min_rel`/`max_rel` も返却 `PackingState` 側とは独立な
  read-onlyコピーとする。（`EMSBox` は `frozen=True` の dataclass だが、`min_rel`/`max_rel`
  自体はNumPy配列であり可変であるため、フィールドの再代入不可というdataclassの性質だけでは
  配列内容の非共有を保証しない。height と同様に、EMSBoxが保持する配列についても明示的に
  独立コピーする必要がある。）返却する `PackingState` とキャッシュ内部の配列は
  height・EMSともに共有しない（どちらかを変更しても他方に影響しない）。
- `build_state_cached` が返す `PackingState` は、キャッシュのヒット/無効化の別によらず、
  常に同一入力に対する `build_state` の結果と height（`np.array_equal`、**完全一致**）・EMS集合
  （§4.3と同じ1e-6丸め、**テスト上の近似比較**）の両方で一致する。**この1e-6丸めはテストが
  出力の同値性を確認するための比較専用であり、上記のキャッシュ有効性判定（AABB署名・
  geometry_key）には一切使用しない**。両者は明確に区別する：キャッシュ判定は丸めない厳密な
  等値比較、出力同値性の検証（テスト）は1e-6丸めの近似比較。丸め署名でキャッシュ判定を行うと、
  1e-6未満の位置変化でcanonicalな `height` が変化するケースを見逃し、`np.array_equal` 完全一致
  の契約を破りうる。

**テスト**

* 往復性質テスト：ランダム点で `rel_to_world(world_to_rel(p)) == p`（1e-12）。origin_world は
  `(offset_x, 0, 0)` の**X成分のみの並進**であり、Y/Zは不変であることも合わせて検証する（§3.1）。
* 回転AABB：`packed_items` の `orn` に**合成クォータニオン**（複数回転のHamilton積）を用いたケースで、
  `rotated_aabb` を経由した `PlacedItem.aabb_min_rel`/`aabb_max_rel` が**解析的に導出した期待値**
  （回転行列を手計算し軸整列半寸法の置換として求めた値）と一致することを検証する（atol=1e-6）。
  公式物理沈降させた `packed_items` golden との一致試験は、対応する fixture が未整備のため
  T-012時点では対象外とし、fixture 整備後の別チケットで追加する。
* EMS・打切り率：空コンテナ（cut・棚なし直方体、既配置0件）について、`build_state` が返す
  `state.ems[idx]` が内壁AABBに一致する EMS 1個であること、`state.ems_truncation[idx] == 0.0`
  であることを検証する。これは `PackingState` への**格納**の確認であり、候補数が予算

  打切り率の受け渡し）は、T-012時点では専用テストを設けない。予算の値自体は
  `tests/test_types.py`（`StageParams().ems_top_n_per_container == 80`）で検証し、`select_topn`
  の切り捨て挙動そのものは既存の `tests/test_ems.py` でカバーする。`build_state` が
  `select_topn` へ定数値を正しく渡していることはコードレビューで確認する（候補数が予算を超える
  決定論的 fixture を用意できた場合は、その時点で非ゼロ打切り率の受け渡しテストを追加してよい）。
* 性能：1回ウォームアップ後、5回計測した**中央値**が500ms未満であることを検証する
  （`time.monotonic()` を使用、§2.4）。ローカルでの目安確認であり、**最終判定は提供CPU評価
  コンテナで実施する**。
* `test_state_rebuild.py`：`build_state_cached` と `build_state` の同値性を検証する。
  height は `np.array_equal` による完全一致、EMSは各座標を1e-6で丸めた6要素tupleの
  ソート済み列としての一致（§4.3と同じ丸め比較）、`ems_truncation` は `math.isclose` で
  比較する。最低限含めるケース：`cache=None` 初回呼び出しでの全再構築フォールバック／
  単一追加・複数追加・逐次複数ステップでのキャッシュヒット／複数追加の順序非依存／
  既配置の物理沈降ドリフト・削除・件数減少・コンテナ形状変更それぞれによる無効化と
  全再構築フォールバック／配置の並べ替えのみ（追加差分なし）での再利用／同一AABBが
  複数存在する多重集合ケース／複数コンテナでヒットと無効化が混在するケースの
  コンテナ単位独立性／cut・棚ありコンテナでの一致／候補数が予算を超え打切りが発生する
  ケースでの選択EMS列・打切り率の一致／キャッシュ内部配列と返却 `PackingState` の
  非共有・`heights` の `writeable=False`／`build_state` と同じ入力非改変契約。
  T-013a時点（本体未実装）では `pytest --collect-only tests/test_state_rebuild.py -q`
  が成功することをもって契約確定の完了とし、T-013bの実装完了後に
  `pytest tests/test_state_rebuild.py -q` 緑をDoDとする。

### 4.5 `masks.py` — 実行可能性判定（段階フィルタ）（T-014〜T-017）

**目的**：候補の合格/不合格と reject_reason を返す。公式 PlacementValidator の幾何部を**移植**し、内部は厳格側マージンで運用する。

**段階識別子 `MaskStage`（T-015確定、`masks.py` 内定義・公開APIの一部）**

段階識別子は物理定数・調整パラメータではなく `masks.py` 固有の処理識別子であるため `constants.py` には置かない。
`IntEnum` は int 互換であり、既存の `evaluate_stage(..., stage: int)` シグネチャと両立する。

```python
from enum import IntEnum

class MaskStage(IntEnum):
    DIMS = 0
    INCLUSION = 1
    OVERLAP = 2
    CEILING = 3
    L_PATH = 4
```

**`evaluate_stage` の意味論（T-015確定）：単一段階ディスパッチ**

`evaluate_stage(state, cand, pp, stage)` は `stage` 以前の判定を累積実行する関数ではなく、
**指定された1段階の判定だけ**を実行し、その結果のみを `cand` へ反映して同じ `Candidate` オブジェクトを返す。

* `feasible=True` は「全段階を通過済み」という意味ではなく、**今回指定された段階を通過した**ことを意味する。
  候補が全段階を通過したかどうかは、呼び出し側（§4.12）が既定の段階順で短絡評価することによって保証する
  （下記「呼び出し側の責務」参照）。
* `stage` は `MaskStage(stage)` として解釈する。定義されていない整数が渡された場合は `ValueError` を送出する。
* `cand.ems_id` は対象コンテナの選択済みEMSリストに対する index である。DIMS 段階の対象EMSは
  `ems = state.ems[cand.container_idx][cand.ems_id]` として解決する。`ems_id` が範囲外の場合の
  自然な `IndexError` は独自に握りつぶさない。
* 対象コンテナ空間は `space = state.containers[cand.container_idx]` として解決する。

各段階が実行する判定と、合格・不合格時の `Candidate` 更新は次のとおり：

```python
def evaluate_stage(state, cand, pp, stage: int) -> Candidate:
    # stage は MaskStage(stage) として解釈する（未定義値は ValueError）。
    # MaskStage.DIMS:      ems = state.ems[cand.container_idx][cand.ems_id]
    #                      ok = prefilter_dims(cand, ems)               / reject_reason="dims"
    # MaskStage.INCLUSION: space = state.containers[cand.container_idx]
    #                      ok = check_inclusion(space, cand, pp)        / reject_reason="inclusion"
    # MaskStage.OVERLAP:   ok = check_overlap(state, cand, tol=-pp.internal_extra)
    #                                                                   / reject_reason="overlap"
    # MaskStage.CEILING:   space = state.containers[cand.container_idx]
    #                      ok = check_ceiling(space, cand, pp)          / reject_reason="ceiling"
    # MaskStage.L_PATH:    T-017以降で ok = check_l_path(state, cand, pp) / reject_reason="path"
    #                      T-015時点では推測実装・暫定合格を行わず NotImplementedError を送出する
    #                      （T-016B で l_path_sweep_boxes/check_l_path を実装、T-017でここへ接続。
    #                      T-016B は T-016A のゴールデン生成・採択率基準確定まで BLOCKED、詳細は
    #                      本節末尾「L字経路：公式契約の事実・T-016A/T-016B」および §6 参照）。
    #
    # ok が True: cand.feasible = True;  cand.reject_reason = ""
    # ok が False: cand.feasible = False; cand.reject_reason = <当該段階の理由>
    # 引数で受け取った cand を更新し、同一オブジェクトを return する。
    ...
```

**呼び出し側の責務（§4.12 本体パイプラインと同一の順序）**：`evaluate_stage` 自体は単一段階しか評価しないため、
「DIMS → INCLUSION/OVERLAP/CEILING →（上位Mのみ）L_PATH」という段階順序と、不合格になった候補へ後続段階を
適用しない短絡評価は、**呼び出し側**（§4.12 手順3・4・6）が規定順に `evaluate_stage` を呼び出すことで実現する。
`evaluate_stage` 内部に短絡パイプラインを持たせない。

**禁止（T-016B）**：`l_path_sweep_boxes`／`check_l_path` の推測実装。公式に対応するAABB幾何が
存在しない部分（レグ形状・マージン反映方法）を README や概念図から独自設計してはならない。
設計は必ず「T-016A ゴールデン上で危険な誤合格0件」という検証可能な安全契約に基づく（§4.5末尾参照）。
A15・プロキシアルゴリズム・採択率下限は v1.13（本節末尾「L字経路：プロキシ確定仕様（v1.13）」）で
確定済み。T-016B実装はこの確定仕様に従う（新たな推測・独自設計を追加しない）。

**性能予算**：dims 1µs／inclusion+overlap+ceiling 合計 <0.3ms／l_path <1ms（p95、いずれも1候補あたり、既配置80個時）。
l_path はT-016B確定（v1.13）でDoDをp95<1.0ms/candidateと定め、`l_path_sweep_boxes`+`check_l_path`を
そのまま呼び出す構成（既配置80個・raw棚1個、状態は`build_state`相当で1回だけ構築しループ外）で
median=0.077049ms／p95=0.094093ms／max=1.144084msを実測しMET（詳細実測条件は
`docs/interface_notes.md` §L）。**この予算達成は「障害物集合（既配置AABB・raw棚AABB）を候補ごとに
再構築しない」実装（既存`PlacedItem.aabb_min_rel/max_rel`・`ContainerSpace.path_obstacle_boxes_rel`の
キャッシュ再利用）を前提とする**。提供CPU評価コンテナでの最終計測は別途T-016B実装時に行う。

**テスト**

*ゴールデン生成条件（v1.12追補で確定。旧「未確定・付録D」は本追補で解消）*

**固定seedとカテゴリ別派生**：基準 `base_seed = 16016`。Python組込み `hash()` はプロセスごとに
値が変わり得るため使用禁止。カテゴリ・ケース単位の派生seedはSHA-256から固定整数を導出する契約とする：

```text
category_seed(category) = int.from_bytes(
    sha256(f"lpath-v1:{base_seed}:{category}".encode("utf-8")).digest()[:8], byteorder="big")
case_seed(category, i) = int.from_bytes(
    sha256(f"lpath-v1:{base_seed}:{category}:{i:04d}".encode("utf-8")).digest()[:8], byteorder="big")
```

**ケース数とcase_id**：合計1,000件。カテゴリ別内訳と公式期待は次のとおり。

| category                 | 件数  | 公式側の期待 |
| ------------------------ | --- | ------ |
| `clear_path`             | 200 | pass   |
| `y_leg_blocked`          | 200 | fail   |
| `x_leg_blocked`          | 200 | fail   |
| `safety_margin_boundary` | 200 | 分布を記録  |
| `random_scene`           | 200 | 分布を記録  |

`case_id` はカテゴリ別連番で固定形式とする：`lpath-v1-<category>-<0000..0199>`。

**カテゴリ契約**：

* `clear_path`：Y・Xレグとも壁・棚・既配置物から十分離す。200/200 pass 必須。1件でも fail
  または例外なら生成失敗
* `y_leg_blocked`：Xレグ・最終配置位置は妨害せず、Yレグだけを明確に遮蔽する。200/200 fail 必須。
  1件でも pass または例外なら生成失敗
* `x_leg_blocked`：Yレグは妨害せず、Xレグだけを明確に遮蔽する。200/200 fail 必須。1件でも pass
  または例外なら生成失敗
* `safety_margin_boundary`：公式 `safety_margin` 境界の内外を重点的に生成する。境界からの摂動値は
  次の8水準×各25件＝200件固定（0mmは mesh 接触形状・浮動小数点境界へ過度に依存するため必須水準に
  含めない）：`-20.0mm / -5.0mm / -1.0mm / -0.5mm / +0.5mm / +1.0mm / +5.0mm / +20.0mm`。
  正負は公式 `safety_margin` 基準に対して負＝衝突域へ近づける、正＝衝突域から離す、と定義する。
  公式pass/fail比率自体は合否条件にせず、水準ごとの件数を報告する
* `random_scene`：有効なコンテナ・候補・既配置物のみを生成し公式処理の例外が発生しないこと。
  container／orientation／目標位置／既配置数を固定seedで変化させ、pass/fail両方を含むこと。
  カテゴリ内でpassまたはfailのどちらかが0件なら生成失敗

`official_exception == 0`。`clear_path`／`y_leg_blocked`／`x_leg_blocked`の構成上これを満たさない
場合はfixture生成または公式呼び出し側の異常と判断する。

**生成試行上限**：カテゴリごとに目標件数の10倍を上限とする：`max_attempts_per_category = 2000`。
200件に到達できない場合は生成条件を黙って緩和せず非ゼロ終了する。

*spyの契約（v1.12再追補で確定。旧「付録D停止・未解決」は本追補で解消）*

`PlacementValidator.check_transport_path` は次の短絡動作を行う（`validator.py`読解で確定済みの
公式事実）：①Yレグの `_move_item` を実行②Yレグが不合格なら即座に `False` を返す（Xレグの
`_move_item` は未実行）③Yレグが合格した場合だけXレグの `_move_item` を実行④Xレグの結果を
最終判定として返す。したがって「例外なしの全ケースで呼び出し2回」という**旧記述は削除**し、
呼び出し回数はケースごとに次のいずれかに確定する：

```text
Yレグ不合格： call_count=1、Xレグ未実行、official_pass=False
Yレグ合格・Xレグ不合格： call_count=2、official_pass=False
Yレグ合格・Xレグ合格： call_count=2、official_pass=True
```

* 元の `_move_item` を必ず呼び出す（差し替えない）。引数・戻り値を変更しない。呼び出し順序を維持する。
  公式コード（`validator.py`）へは変更を加えない
* 必須：全1,000件について spy有無で公式の最終bool（`is_packable`／`check_transport_path`の
  返り値）が一致すること（`spy_boolean_mismatch == 0`）。比較は「spyなし」「spyあり」の同一ケースを
  それぞれ実行して最終boolを比較する。一方の実行によるPyBullet状態変更が他方へ影響しないよう、
  同じシリアライズ入力から環境を再構築するか同一の保存状態（`saveState`/`restoreState`）へ
  復元してから実行する契約とし、実行順序に依存して結果が変わる状態を許容しない

**spyの記録形式**：単なる目標位置配列ではなく、呼び出し単位の記録を保存する。

```json
{
  "move_calls": [
    {"leg": "y", "target_pos": [0.0, 0.0, 0.0], "passed": true},
    {"leg": "x", "target_pos": [0.0, 0.0, 0.0], "passed": false}
  ]
}
```

* 1件目は必ず `leg="y"`。2件目が存在する場合は `leg="x"`
* Yレグ不合格時はXレグの記録を作らない（架空の値で埋めない、`move_calls`配列長1）。
  `move_calls`は配列そのものが可変長であるためXレグ欠損を表現でき、個別フィールドを
  `null`で埋める必要はない（配列長＝`move_call_count`が明示値として機能する）
* spyは元の `_move_item` の戻り値も変更せず記録する

**カテゴリ別のspy要件**：

* `clear_path`：`move_call_count==2`、`move_calls[0].leg=="y" and passed is True`、

**L字経路：プロキシ確定仕様（v1.13、2026-07-19）**

`ContainerSpace`の派生フィールド定義は§4.2「T-016B: L字経路用派生フィールド」を正とする。以下は
プロキシ判定アルゴリズムそのものの確定仕様。

*比較したプロキシ候補と実測結果*（T-016Aゴールデン全1,000件、design 600件/holdout 400件の
sha256順層化分割・boundary8水準を含む。詳細な実測手順・数値は`docs/interface_notes.md` §L）：

| 候補 | 判定式 | 危険な誤合格（全1000） | `proxy_acceptance_rate`（分母403） | 採否 |
| --- | --- | --- | --- | --- |
| P1 | `max(gap) > safety_margin + EPS_GEOM` | 0 | 403/403 = 1.000000 | 記録のみ、不実装 |
| P2 | `max(gap) > safety_margin + internal_extra + EPS_GEOM` | 0 | 316/403 = 0.784120 | 記録のみ、不実装 |
| P3 | P1と分配則（AABB膨張の可換性）で数学的に同値 | — | — | 記録のみ、不実装（同値性確認のみ） |
| **P4（採用）** | `distance_sq > (safety_margin + EPS_GEOM) ** 2` | **0** | **403/403 = 1.000000** | **採用** |

*採用プロキシ（P4）の確定式*：`gap`はスイープAABB `A` と障害物raw AABB `B` の軸ごとの隙間

```python
gap = np.maximum(0.0, np.maximum(a_min - b_max, b_min - a_max))  # shape (3,)、重なる軸は0
distance_sq = float(np.dot(gap, gap))
pass ⇔ distance_sq > (pp.safety_margin + EPS_GEOM) ** 2
```

**L字経路では`pp.internal_extra`を加算しない**（他段階＝inclusion/overlap/ceilingとは異なる方針。
下記の片側安全性証明が`safety_margin`単独で成立するため、追加の厳格化は採択率を不必要に下げるのみ
と判断した）。境界の等号・接触・浮動小数誤差はすべて不合格側（`EPS_GEOM`により厳密に不等号側へ
倒す。新規local magic numberは追加せず既存`EPS_GEOM`をそのまま使用する）。

*片側安全性の式的証明*：2つのAABB `A`,`B`が分離している場合、軸ごとの隙間`gap_i`（重なる軸は0）
について、真のユークリッド距離は`d(A,B) = sqrt(Σgap_i²) = sqrt(distance_sq)`（非分離軸は寄与せず、
分離軸のみピタゴラスで合成されるため）。よって`distance_sq > margin² ⇔ d(A,B) > margin`
（両辺非負のため平方は単調）。各AABBは対応collision bodyの超集合であるため
`d(A,B) <= 真のmesh間最短距離`（超集合同士の最短距離は部分集合同士の最短距離以下）。
ゆえに`d(A,B) > safety_margin ⇒ 真のmesh間最短距離 > safety_margin ⇒ 公式pass`。
`proxy_pass ⇒ official_pass`の片側含意が式で確認できる。

*P1とP4がゴールデン全1,000件で完全一致した理由*：221件で最近接obstacle-legペアが2軸以上で分離
（対角分離）していたが、いずれも`clear_path`等の大マージンケースでどちらの閾値でも余裕でpassする。
境界（boundary/blocked）カテゴリの閾値ぎりぎりのケースは生成設計上すべて単一軸分離であり、
そこでは`max(gap)`と`sqrt(distance_sq)`が数学的に厳密一致するため、両候補は本ゴールデン上では
区別できない。P4を採用する理由は、本ゴールデンが未網羅の対角分離境界ケースに対しても理論的な
安全マージンが最大になるため（P1は対角分離ケースを不要に過剰棄却しうる）。

### 4.6 `stability.py` — 幾何安定性プロキシ（T-020〜T-021）

**公開API**

```python
def support_ratio(state, cand) -> float
    # 底面セル（cells_of_aabb）のうち、height[i,j] >= cand底面z - TOL_CONTACT
    # を満たすセル面積比。床（floor_z）支持も同条件で含む。0..1
def support_polygon(state, cand) -> np.ndarray   # shape (K,2)
    # 支持セルが表す矩形接触パッチ（各セルの生矩形を候補底面AABBおよびコンテナ内壁XYで
    # クリップしたもの）の全頂点の凸包（Andrew monotone chain を numpy で実装。scipy 禁止）。
    # v1.14で「支持セル中心点の凸包」から訂正（本節末尾の更新履歴参照）。
def cg_margin(state, cand) -> float
    # 荷物中心 (x,y) から凸包境界までの符号付き距離（内側+／外側−）。
    # K<3（点・線支持）のときは -inf 扱い（=不安定）
def max_step_below(state, cand) -> float          # 底面下の height の最大段差
def soft_below_ratio(state, cand) -> float        # 支持セルのうちソフト荷物上面の比率
```

**monotone chain 擬似コード**（実装指示）：点集合を (x,y) 辞書順ソート→下側凸包→上側凸包→連結。同一点は事前に `np.unique`。

**テスト**

* 平床に置く → support_ratio=1.0、cg_margin = min(osize.x, osize.y)/2（正方支持なら辺長/2、許容 1e-3）
  （支持パッチ凸包が候補底面境界と一致するため成立。セル中心のみの凸包では半セル分内側にずれ
  許容誤差を満たさないことをv1.14で確認・訂正済み、本節末尾の更新履歴参照）
* 0.4×0.4 底面の半分が 0.2 幅の台に載る → support_ratio ≈ 0.5、CG は台の縁上 → cg_margin ≈ 0.0（|値|<1cm）
  （支持パッチ凸包の境界が台の縁 x=0.0 と一致するため成立）
* 2点支持（K=2）→ cg_margin = -inf

**v1.14 追補（support_polygon 定義の訂正）**：T-021実装時、旧記述「支持セル中心点の凸包」を
そのまま実装すると、上記2つのテスト期待値（平床0.20・半分支持0.0）を cell=0.02 の標準
fixture上で満たせないことが判明した（セル中心のみの凸包は候補底面の実境界より cell/2=0.01
だけ内側になり、許容誤差 1e-3 を超える差・半分支持での strict な境界条件不成立が生じる）。
これを受け、support_polygon の定義を「支持セルが表す矩形接触パッチ（各セルの生矩形を候補
底面AABBおよびコンテナ内壁XYでクリップしたもの）の全頂点の凸包」へ訂正した。これはセル
中心凸包への事後的な cell/2 加算・膨張ではなく、各格子セルが本来表す接触面積をそのまま
復元する定義であり、平床0.20・半分支持0.0 の双方に数値的に一致する。

`now_fn` で fake clock 注入）／新しい独自timeout実装を追加しない。

**候補集合の共有（T-024、全層で再列挙しない）**：1回の `policy` 呼出しで作成した次の集合を全層が参照する
（§4.12「候補列挙・候補生成契約」で生成順を確定）。

```
raw_candidates:  item×container×orientation×EMS から生成した全候補（§4.12）
dims_candidates: raw_candidates のうち DIMS 通過。provisional_p_ng 計算済み（§4.7）
geo_candidates:  dims_candidates のうち INCLUSION+OVERLAP+CEILING も通過
path_candidates: geo_candidates のうち L_PATH 通過（層をまたいで随時追加される）
```

L_PATH判定結果は `Candidate` 単位でキャッシュし、同一候補への `check_l_path` 重複呼び出しを行わない
（layer1で評価済みの候補をlayer2が再評価しない）。基本順序（決定論・全層・同点tie-breakで共通使用）：
`pool現在順 → container_idx昇順 → orientation昇順 → ems_id昇順`。**`ems_id` は `state.ems[container_idx]`
（＝ `select_topn` 出力リスト）内の0始まりindexと定義し、`ems_id`昇順は`select_topn`が返す順序と同義
である**（§4.3 T-011「決定的ソートキー」）。

`CandidatePools`/`CandidateKey` を参照する）は、ファイル先頭で `from __future__ import annotations`

**4層の定義（入力・評価・戻り条件を一意に規定）**

* **layer1_main**：入力＝`geo_candidates` を `heuristic_score` 降順に並べた上位 `StageParams.l_path_top_m`
  件（**policy全体でL_PATHが上位M件のみに限定されるという意味ではない**。layer2が追加評価し得る、下記
  参照）。上位M件だけに `check_l_path` を実行し、合格した候補のうち `heuristic_score` 最大を返す
  （同点は基本順序）。soft超過時はその時点までに確認済みの最良L_PATH合格候補を返す。合格候補が無い、
  または層内で例外が発生した場合は `None`。`effective_score`・学習済み `p_ng` は使わない（T-024時点）。
* **layer2_dblf_strict**：入力＝`geo_candidates`。layer1で `check_l_path` が未評価だった候補を基本順序で
  評価する（**hard期限内に限り、layer1のM件を超えて残りの`geo_candidates`を追加評価できる**。評価済み
  候補はキャッシュ結果を再利用し重複呼び出ししない）。DIMS/INCLUSION/OVERLAP/CEILING/L_PATHの全5段階
  合格を必須とし、最初の合格候補（基本順序）を返す。hard超過後は新しい `check_l_path` 評価を開始しない。
  候補なし・時間切れ・層内例外のいずれでも `None`。`strict` は全5段階を省略しない意であり、新規の
  `support_ratio`／`cg_margin` 閾値は追加しない。
* **layer3_first_fit**：入力＝`geo_candidates`。新しい高コスト処理（追加のL_PATH評価等）は行わない。
  L_PATHの既知状態がある候補は「pass→未評価→fail」の順に優先し、各群内は基本順序で並べ、先頭を返す。
  L_PATH合格は必須としない。候補なし・層内例外なら `None`。時間切れ時の低コスト縮退であり、validator
  NGの可能性はあるが Agent 例外を防ぐための層。
* **layer4_max_p**：入力＝`dims_candidates`。追加のマスク・L_PATH・特徴計算は開始しない。事前計算済み
  `provisional_p_ng` が最小（＝`p_success`最大）の候補を返す（同点は基本順序）。`dims_candidates` が
  空、または層内例外なら `None`。幾何合格（DIMS以降の段階）を保証しない最終Candidate層である。

**各層の詳細契約（v1.17、Q3確定内容。上記概要を補い一意化する）**：

* `layer1_main`：`pools.geo_candidates` を `cand.score` 降順で**安定sort**する（同点はsort前の
  `geo_candidates`順＝基本順序）。`stage_params.l_path_top_m` 件だけを対象とする。
  `l_path_top_m <= 0` の場合は `check_l_path` を一切呼ばず `None` を返す。上位対象を順に評価し、
  `pools.l_path_cache` 未登録なら `check_l_path` を呼びキャッシュへ記録、登録済みなら再利用する。
  合格候補のうち `cand.score` 最大のものを返す（同点は基本順序）。合格時は `pools.path_candidates`
  へ同一Candidateを1回だけ追加する。soft超過を検出した時点で、その時点までに確認済みの最良合格
  候補を返す（未評価候補へ進まない）。hard超過後は新しい `check_l_path` 評価を開始しない。
* `layer2_dblf_strict`：`safe_decide` の層順序により、layer1で確定しなかった場合のみ呼ばれる。
  `pools.geo_candidates` を基本順序で走査する。`pools.l_path_cache` に登録済みの候補は
  `check_l_path` を再呼出しせずキャッシュ値を再利用する。未評価候補は、hard期限内に限り追加で
  `check_l_path` を1回だけ呼びキャッシュへ記録する。最初のL_PATH合格候補（基本順序）を返す。
  hard超過後は新規評価を開始せず、それまでの評価結果に合格が無ければ `None`。
* `layer3_first_fit`：新しい `check_l_path` 評価を行わない（`l_path_cache` の既存値のみ参照）。
  `pools.geo_candidates` を次の3群に安定分類する：(1) `l_path_cache` が `True`、(2) `l_path_cache`
  にキーが無い（未評価）、(3) `l_path_cache` が `False`。各群内は基本順序を維持し、群の優先順位
  (1)→(2)→(3) で先頭のCandidateを返す。
* `layer4_max_p`：`pools.dims_candidates` のみを使用する。`cand.p_success` が**有限**である
  Candidateの中から最大値（＝`provisional_p_ng` 最小）を返す。`p_success` が非有限（NaN/Inf）の
  Candidateは選択対象から除外する。同点は `dims_candidates` の元順（基本順序）。全Candidateの
  `p_success` が非有限なら `None`。

**L_PATHキャッシュ（v1.17新設）**：`CandidatePools.l_path_cache: dict[CandidateKey, bool]`
（`CandidateKey` は §4.12「candidates.py 公開API契約」参照）。`True`=評価済み・合格、`False`=
評価済み・不合格、キー不在=未評価。`None`は値として保存しない。`layer1_main`/`layer2_dblf_strict`
はこのキャッシュを共有し、同一キーへ `check_l_path` を再呼出ししない（pass/fail双方をキャッシュ
する）。

```python
def safe_decide(layers: list, state, budget: StepBudget,
                telemetry: dict) -> Candidate | None

    # 契約: (a) budget_poll_every 件ごとに budget を確認し超過なら None を返す
```

**`safe_decide` telemetry契約（v1.17新設）**：呼出し開始時に
`telemetry.setdefault("decided_layer", 0)`／`telemetry.setdefault("layer_error", [])`。各層で
例外を捕捉した場合 `telemetry["layer_error"].append({"layer": layer_index, "error_type":
type(exc).__name__})`（`layer_index` は1〜4。例外メッセージ・トレースバック全文は格納しない）。
例外後は次層へ進む。Candidateが返れば即 `telemetry["decided_layer"] = layer_index` として確定し
返す。全層 `None` または全層例外なら `decided_layer` は初期値 `0` のまま `None` を返す。
`safe_decide` 自身は `make_action` を呼ばず、Candidateを変更しない。全層が同一 `state`／同一
`budget` オブジェクトを共有する。`safe_decide` 自体は例外を外へ送出しない（各層の例外は内部で
捕捉し記録する）。

**最外殻 emergency action（safe_decide の外側、`agent.policy()` 最外殻の責務）**：次のいずれかの場合、
`safe_decide` を介さず `make_action()` で emergency action を返す——(a) state再構築（`build_state`）例外、
(b) `raw_candidates` が0件、(c) `dims_candidates` が0件、(d) `safe_decide` が `None` を返した、
(e) 全層で例外、(f) `Candidate`→action変換時の例外。正常な `observation` から現在プール先頭の公式indexを
読める場合は `item_idx=int(observation["pool_list"][0]["index"]), container_idx=0,
pos_rel=(0.0,0.0,0.5), orientation=0`。プールindexすら取得できない異常入力の場合に限り、T-023の
固定プレースホルダー定数 `item_idx=0` を使う。emergency actionでも `telemetry["decided_layer"]=0` の
材料を保持する（JSONL正式出力はT-028）。この最外殻actionは合法配置を保証せず、公式I/Fにskipが存在しない
状況でAgent例外・`format_error` を避ける最後の手段であり、validator NGは許容する。T-023の固定
placeholderは、この最外殻緊急actionとしてのみ限定的に残す契約とし、正常な候補ゼロ時の主フォールバック
（layer4）とは区別する。

**候補列挙・候補生成契約（v1.16新設、T-024）**

*列挙順（決定論・§4.11「基本順序」と同一）*：`pool の現在順（build_state 構築順、A11） →
container_idx 昇順 → orientation 昇順(0..5) → state.ems[container_idx]（select_topn出力）の
ems_id昇順（0始まり index、select_topn順と同義、§4.3 T-011）`。同点tie-breakも同じ順序を使用し、
set/dict の偶然の順序へ依存しない。T-037/T-038 が選択・配分戦略を置換しても最終tie-breakの決定論性は
維持する。

*DIMS/EMS方針（案A：全EMS独立列挙、採用）*：現行の列挙は `item × container_idx × orientation × 各EMS`
の完全直積である（`ems.select_topn`が各コンテナのEMSを既に決定論的に確定済み）。DIMS不合格の
Candidateはその組合せを破棄し、post-hocな`ems_id`付替え・別EMSへの再割当は行わない。「別EMSなら
置ける」ケースは、同じ荷物・姿勢が別EMSに対して生成される別Candidateとして完全列挙が自然に回収する。
再割当を行わないため、再割当専用のtelemetryキーは追加しない。

*候補位置生成式（`Candidate.pos_rel`、1件/(item,container,orientation,EMS)）*：本プロジェクトの
コンテナは開口部がY−側・奥がY+側であり、`heuristic_score`も「低いZ・奥(+Y)・若いX」を優先する
（§4.8）。DBLF最小角（全3軸ではなく、X=若い側／Y=奥(+Y)へ寄せる／Z=EMS支持面へ底面一致）で固定する。
中心候補・複数角候補は生成しない（候補不足が実運転で確認された場合の後続改善とする）。

```python
xy_required_clearance = max(-pp.inclusion_margin + pp.internal_extra, pp.internal_extra)
xy_generation_clearance = xy_required_clearance + pp.candidate_generation_slack

pos_rel[0] = ems.min_rel[0] + osize[0] / 2.0 + xy_generation_clearance   # X: 若い側へ寄せる
pos_rel[1] = ems.max_rel[1] - osize[1] / 2.0 - xy_generation_clearance   # Y: 奥(+Y)へ寄せる
pos_rel[2] = ems.min_rel[2] + osize[2] / 2.0                              # Z: 支持面へ底面一致
```

`xy_required_clearance` は現行値（`inclusion_margin=-0.005`／`internal_extra=0.005`）で
`max(0.005+0.005, 0.005)=0.010`。`candidate_generation_slack=1e-6`（§3.5、`PlacementParams`）を
加えた `xy_generation_clearance=0.010001` が実際に使う値。**実装は `0.010001` を直書きせず、必ず
`PlacementParams` の各フィールドから導出する**。アンカー側1面（X若い側・Y奥側）にのみXYクリアランスを
入れる式であり、**全6面へ一律に余裕を入れる仕様ではない**。

*Z方向の契約（支持面側を一律に浮かせない）*：候補底面は `ems.min_rel[2]` に厳密一致させ、
`candidate_generation_slack` を加算しない（支持面側Zへslackを加えて荷物を浮かせる仕様は禁止）。
天井側も候補生成時には新しい余裕を入れず、既存CEILINGマスクの判定（`pp.ceiling_margin+pp.internal_extra`、
§4.5）へ委譲する。L_PATHは既存どおり `pp.safety_margin` のみで判定し、`internal_extra`も
`candidate_generation_slack`も加算しない（§4.5「L字経路：プロキシ確定仕様（v1.13）」不変）。

*候補生成前の寸法確認*：次を全て満たす場合のみCandidateを生成する（アンカー側1面のみにXYクリアランスを
要求する式。これは事前枝刈りであり、正式合否は引き続きDIMS→INCLUSION→OVERLAP→CEILING→L_PATHの
各マスクが判定する。候補生成式だけで合格を保証したことにはしない）：

```python
ems.size()[0] >= osize[0] + xy_generation_clearance
ems.size()[1] >= osize[1] + xy_generation_clearance
ems.size()[2] >= osize[2]
```

*float32往復の境界検証（`candidate_generation_slack`の決定試験）*：
`float64 Candidate.pos_rel → make_action() → float32 place_pos → float64へ復元 →
DIMS/INCLUSION/OVERLAP/CEILING 再判定` の手順で、`candidate_generation_slack=1e-6` により現行の

candidate生成専用fixtureは現時点で存在しないため、本書は「検証済み」とは書かない。T-024テスト設計

**`candidates.py` 公開API契約（v1.17新設、T-024所有）**：候補列挙・段階フィルタの構築を
`src/packing_core/candidates.py` が所有する。

```python
from dataclasses import dataclass, field

CandidateKey = tuple[int, int, int, int]  # (item_idx, container_idx, orientation, ems_id)

@dataclass
class CandidatePools:
    raw_candidates: list[Candidate]
    dims_candidates: list[Candidate]
    geo_candidates: list[Candidate]
    path_candidates: list[Candidate] = field(default_factory=list)
    l_path_cache: dict[CandidateKey, bool] = field(default_factory=dict)
    reject_counts: dict[str, int] = field(default_factory=dict)

def candidate_key(cand: Candidate) -> CandidateKey: ...

def candidate_from_ems(
    item: ItemSpec, container_idx: int, orientation: int, ems_id: int,
    ems: EMSBox, pp: PlacementParams,
) -> Candidate | None: ...

def enumerate_candidates(
    state: PackingState, pp: PlacementParams, tp: TimeParams, budget: StepBudget,
) -> list[Candidate]: ...

def filter_candidates(
    state: PackingState, raw_candidates: list[Candidate],
    pp: PlacementParams, tp: TimeParams, budget: StepBudget,
) -> CandidatePools: ...
```

契約：

* `CandidateKey` は `(item_idx, container_idx, orientation, ems_id)` の順（すべて組込みint）。
* `candidate_from_ems`：`oriented_size(item.size, orientation)` で `osize` を求め、上記「候補位置
  生成式」のアンカー式で `pos_rel` を求める。上記「候補生成前の寸法確認」を満たさなければ `None`。
  満たせば `item_idx=int(item.idx)` 等、正しい `container_idx`/`orientation`/`ems_id`（すべて
  組込みint）を持つ新規Candidateを1件返す。入力の `ItemSpec`/`EMSBox`/配列を変更しない。
  `prefilter_dims` 等のmaskはここでは呼ばない。別EMSへの再割当は行わない（案Aを維持）。
* `enumerate_candidates`：`pool現在順→container_idx昇順→orientation 0..5→ems_id昇順`
  （`select_topn`出力順と同義）の完全直積を、`candidate_from_ems` が `None` を返さないものだけ
  順序維持のまま返す。set/dict変換で順序を失わない。mask判定・score・L_PATHは行わない。新しい
  `StepBudget` を生成しない。
* `filter_candidates`：`raw_candidates` を基本順序のまま、`DIMS→INCLUSION→OVERLAP→CEILING`
  の順に `masks.evaluate_stage` を用いて短絡評価する。最初の不合格段階だけを `reject_counts` へ
  計上し、不合格候補へ後続段階を適用しない。DIMS通過を `dims_candidates`、4段階通過を
  `geo_candidates` に格納する。`path_candidates`/`l_path_cache` は空で初期化する（L_PATH・
  score・risk計算はここでは行わない）。
  **途中終了時の集合契約**：`raw_candidates` は**入力全体をそのまま保持**する（縮小しない）。
  `dims_candidates`/`geo_candidates`/`reject_counts` は**処理済みprefixのみ**を反映し、
  未処理のCandidateは変更しない（`feasible`/`reject_reason`は既定値のまま）。したがって
  `n_cand0`（`len(raw_candidates)`）は filter の時間切れによって減少しない。減るのは
  `n_after_dims`/`n_after_geo` のみである。

**budget確認位置の固定契約（v1.17新設）**：`enumerate_candidates`／`filter_candidates` は関数
開始時に直ちに `budget.over_soft()` を確認する。既に超過していれば、それ以上いかなる候補も処理せず
戻る（`enumerate_candidates`は空リスト。`filter_candidates`は `raw_candidates` を入力全体のまま・
`dims_candidates`/`geo_candidates`/`reject_counts` を空とした `CandidatePools` を返し、未処理の
Candidateは変更しない）。超過していなければ処理を開始し、以後 `tp.budget_poll_every` 件の組合せ／
Candidateを処理するたびに再度 `budget.over_soft()` を確認する。超過を検出した時点で次の未処理候補は
処理せず、その時点までの処理結果（部分リストまたは部分`CandidatePools`）を返す。
`tp.budget_poll_every <= 0` の場合は `ValueError` を送出する。`over_hard()` は
`policy_soft <= policy_hard`（`TimeParams`既定）の関係上 `over_soft()` の超過を包含するため、
本2関数では追加のhard専用分岐を設けない（hardによる「新しい高コスト処理を開始しない」という運用は、
より高コストな `check_l_path` を扱う `layer1_main`/`layer2_dblf_strict` 側、§4.11で個別に行う）。

**Agent配線契約（v1.17新設、Q5相当）**：`filter_candidates` が返す `dims_candidates` の各候補へ、
特徴計算段階で次の順に設定する。

```python
sr = support_ratio(state, cand)
margin = cg_margin(state, cand)
p_ng = provisional_p_ng(support_ratio=sr, cg_margin=margin, params=self.provisional_risk_params)
cand.p_success = float(np.clip(1.0 - p_ng, 0.0, 1.0))
cand.score = heuristic_score(state, cand, self.score_params)
cand.features["support_ratio"] = float(sr)
cand.features["cg_margin"] = float(margin)
cand.features["provisional_p_ng"] = float(p_ng)
```

`cand.p_success` は常に有限・`[0,1]`。NaNを保存しない。`provisional_p_ng` の式を `agent.py` へ
重複実装しない。`heuristic_score` 自身はCandidateを変更しない（代入は呼び出し側=agent.pyの責務）。
専用の公開ヘルパ関数は設けず、`Agent.policy` 内の配線として実装する。

**telemetryローカル辞書契約（生成タイミングを含む、v1.17明確化）**：`policy` 呼出しごとに、
`filter_candidates` 完了後・`safe_decide` 呼出し**前**に新規辞書を生成する。`n_lpath_pass` は

## 7. Phase 5 以降の実装指針（モジュールレベル）

弱いエージェントに任せるのは**枠組みとテストが確定した部分のみ**。ハイパーパラメータ・ネット構造は設計書 §6/§9 の数値をそのまま使い、エージェントに選ばせない。

### 7.1 `training/env_wrapper.py`（T-040）

* `compute_potentials(state) -> dict[str, float]`：evaluator 移植式で fill/cog/stability_proxy/placement/soft の各ポテンシャル Φ_k を算出
* 報酬 `r_t = Σ_k w_k (Φ_k(s_t+1) − Φ_k(s_t))`、終端で公式スコアを加算。NG 終了は「以後のポテンシャル獲得を失う」ことで自然に罰となる（追加の死亡ペナルティ定数を勝手に足さない）

### 7.2 `training/fast_env.py`（T-041）

* 契約：observation の辞書スキーマは公式と同一キー（interface_notes の転記表）。物理なし（置いた位置に確定）
* 一致テスト：ランダム 20 エピソードで、各ステップ後の height を公式 env と比較（許容＝cell 相当。物理沈降差はテスト用に「軽量・低摩擦アイテムのみの config」で抑える）

### 7.3 `training/adversary.py` v0（T-042）


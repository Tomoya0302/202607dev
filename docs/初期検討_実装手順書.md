## 0. 本書の目的と方針

`docs/初期検討.md` の設計（EMS候補生成 → 方策スコアリング → 実行可能性マスク → 課題別デコード、多層フォールバック）を、公式シミュレータ（`simulator/`）の実インターフェースに落とし込むための作業手順を定める。

**開発の五原則**（★v2: 4・5 を追加）

1. **常に提出可能**：どの時点でも `sample_submit` 形式で動く成果物を維持する（壊れた main を作らない）
2. **1手のNGが全てを壊す**：評価基盤では配置検証NGで**その時点でエピソード終了・その状態で採点**。エージェント内部で公式と同等以上に厳しい自己検証を必ず通してから action を返す
3. **タイムアウトは事実上の失格**：`policy` 超過時は**ランダム行動**が代入される（≒NG→エピソード終了）。内部ウォッチドッグで制限時間の1秒以上手前にフォールバック解を返す
4. ★v2 **期待スコアで判断する**：最適化対象は充填率ではなく **E[スコア] = Σ(その手までの生存確率 × 得点)**。配置候補の評価は常に P(配置成功) で重み付けし、「一定数」閾値の到達前後でリスク許容度を切り替える（保守レジーム → 強気レジーム）
5. ★v2 **公式実装が審判**：ローカルの `validator.py` / `evaluator.py` を仕様の唯一の正とする。読解・転記に留めず**移植＋出力一致テスト**で固定し、**ラベル生成器・敵対ループの審判**として使い倒す。LB は「ローカル再現との乖離検知」に用いる（重みの逆推定は行わない）

**戦略スタンス**（★v2）：主戦力は**探索つきヒューリスティック**。RL は加点要素として **C → B → A** の順（限界効用の高い順）に投資し、Phase 6 の Go/No-Go ゲートで継続可否を判定する。

## 1. 公式仕様の要点（実装中に常時参照）

### 1.1 エージェントI/F（`agents/<name>/agent.py`、クラス名 `Agent`）

| メソッド                           | タイミング             | 制限時間（評価基盤） | 要点                                                        |
| ------------------------------ | ----------------- | ---------- | --------------------------------------------------------- |
| `__init__(module_path)`        | 1回                | 10s        | モデル・設定の読込。★v2: **ダミー1手のウォームアップ**（推論1回・キャッシュ生成）もここで        |
| `get_init_states(init_states)` | 1回                | ―          | `optimize` / `lookahead_k` / `container_list` を受領し内部状態を構築 |
| `optimize(item_list)`          | optimize=true時に1回 | **180s**   | 全荷物を見て**積付順（index の並び）**を返す。過不足なく全 index を返すこと            |
| `policy(observation)`          | 毎ステップ             | **8s**     | `{item_idx, container_idx, place_pos, orientation}` を返す   |

* メモリ上限 12GB。評価基盤はインターネット接続不可
* `optimize` タイムアウト → 元のストリーム順で続行（減点はないが機会損失）。`policy` タイムアウト → ランダム行動（ほぼ即死）

### 1.2 座標系・アクション

* Z-up右手系。X=幅、Y=奥行（**開口部は Y マイナス側**＝横空きコンテナ）、Z=高さ。単位は m / kg / s
* `place_pos` は**荷物中心**の、コンテナ原点 `(offset_x, 0, 0)` からの**相対座標**（`offset_x = float(container_list[i]['center'][0])`。`spacing` は agent I/F に存在しないため使用しない。`container_list[i]['center']` が原点世界Xの取得元＝公式 `local_to_global` 由来）。`container_list[i]['center']`・`packed_items` の `pos` は**世界座標**なので変換を一元管理する
* `orientation` は 0〜5 の軸整列6姿勢（0:[L,W,H] / 1:X90°[L,H,W] / 2:Y90°[H,W,L] / 3:Z90°[W,L,H] / 4:Y90→Z90 / 5:X90→Z90）
* **既配置荷物は物理沈降で軸整列とは限らない**（`orn` クォータニオン保持）。状態復元時は回転後AABBで扱う

### 1.3 配置検証（PlacementValidator、評価基盤パラメータ）

| 判定         | 内容                                                                                      | パラメータ                                                                   |
| ---------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 包含判定       | コンテナ枠外へのはみ出し                                                                            | `inclusion_margin = -0.005`                                             |
| **搬入経路判定** | 入口から `目標z + start_z` の高さで **Y軸方向に前進 → X軸方向に横移動** の**L字経路**上の干渉。地面・棚・天井に近い場合 `start_z=0` | `safety_margin = 0.015`, `start_z = 0.08`                               |
| 定着判定       | 落下後のずれ                                                                                  | `displacement_threshold = 0.3`, `angle = 45°`, `settle_wait_step = 300` |
| 天井余裕       |                                                                                         | `ceiling_margin = 0.018`                                                |

> **設計書からの補正1（v1より継承）**：初期検討.md の「上方リフト＋前面直線搬入」仮定に対し、実仕様は **「z+0.08 の高さで Y前進→X横移動のL字スイープ」**。`masks.py` の可達性判定はこの軌跡で実装する。
>
> ★v2 **設計書からの補正2**：公式I/Fに**スキップ行動は存在しない**（policy は必ず配置を返す）。初期検討.md §10 第4層「SKIP_item_safely（安全にスキップ）」は実行不可能のため、**「実行可能候補ゼロ時は P(配置成功) が最大の1手を返す」**へ改訂する（Phase 0 で設計書を対更新）。
>
> ★v2 **補正3（判定の信頼度階層）**：包含・L字経路・天井は**幾何で厳密に再現可能**（コード移植対象）。一方、**定着判定は物理シミュそのもの**であり幾何プロキシでは原理的に再現できない。よって定着リスクは Phase 4 の **P(配置NG) 予測器**（公式シミュで生成したラベルによる学習モデル）で確率として扱う。

### 1.4 評価スコアと課題対応

* スコア = **fill / cog（低重心） / stability（揺らし試験） / placement（優先） / soft_item** の加重平均。**一定数以上積めないと fill 以外 0** → `num_placed_items` を最優先で確保
* 課題との対応（**仮定 A1・要確認**）：**課題A** = `optimize: true`（180sで順序決定→順序固定で `policy`）／**課題B** = `lookahead_k ≈ 20`／**課題C** = `lookahead_k = 1`
* 評価基盤の課題はローカル `sample_config.json` と**全く異なる**（コンテナ数・寸法・荷物分布・順序）。ハードコード禁止、全て `init_states` / `observation` 駆動で実装
* ★v2 **目的関数の明確化**：NG即終了の構造下では、貪欲な充填最大化は期待値で損をし得る。序盤のNGは残り全手荷物を道連れにするため、**手番が浅いほどリスクの価値は高い**。実装上は §0 原則4（リスク調整・2レジーム）に従う

## 付録B：v1 からの設計判断の変更理由（要約）

| 状態管理       | 増分更新で高速化   | 物理沈降で内部状態が真値からドリフトし終盤NGの主因になる   | ステートレス再構築が原則、増分はキャッシュ                        |
| パリティ分布     | ランダム配置で検証  | 本番でNGを踏むのは自エージェントが選ぶ境界ギリギリの手    | 実運転ログ＋境界摂動を追加した3分布                           |
| 目的関数       | 充填率最大化＋制約  | NG即終了＋一定数閾値の下では E[スコア] と乖離      | リスク調整（score×P(成功)）＋2レジーム                     |
